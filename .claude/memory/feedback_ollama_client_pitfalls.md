При подключении Python/Node-кода к локальной Ollama на реальной пользовательской машине
(не в чистом контейнере) напоролись на две проблемы, обе — не баги наших скриптов, а
особенности окружения, которые легко принять за баг библиотеки:

**1. `OLLAMA_HOST` как переменная окружения для клиента — плохая идея.**
На машине уже была системная `OLLAMA_HOST=0.0.0.0` (и ещё `192.168.1.11` на уровне Machine) —
это конфигурация для **сервера** Ollama ("слушать все интерфейсы" / LAN IP), выставленная
её собственным инсталлятором или пользователем ранее (тот же LAN IP фигурирует в старом
`.clinerules` проекта `PlatPhas`, значит используется намеренно для чего-то другого).
Наш код читал `os.environ.get("OLLAMA_HOST", default)` для клиентского подключения и получал
это чужое значение вместо default — `ollama.AsyncClient` не мог подключиться, ошибка выглядела
как "Ollama не запущена", хотя она прекрасно работала. **Why:** оба клиентских SDK и обычный
пользовательский конфиг Ollama используют одно и то же имя переменной для разных целей.
**How to apply:** для клиентских подключений к Ollama никогда не полагаться на общесистемную
`OLLAMA_HOST` без явной проверки — использовать своё имя переменной (например
`LIGHTRAG_OLLAMA_HOST`) с дефолтом `http://127.0.0.1:11434`, не `localhost` (чтобы не зависеть
от резолва в `::1` на машинах, где Ollama слушает только на IPv4).

**2. `num_ctx` (размер контекста) в опциях модели Ollama — не ставить бездумно большим.**
Запрос с `num_ctx: 32768` не укладывался и в 180 секунд (для тривиального промпта), а
`num_ctx: 8192` грузился ~20-23 секунды один раз (дальше быстро, пока модель в памяти).
Обычный запрос без явного `num_ctx` — 2-3 секунды. На видеопамяти со скромным запасом
пересборка KV-cache под большой контекст запредельно медленная (похоже на переполнение VRAM
и откат на CPU/своп). **Why:** LightRAG-подобные пайплайны из документации/примеров часто
советуют выставлять большой `num_ctx` "на всякий случай" — на слабом железе это ловушка.
**How to apply:** начинать с разумного значения (4096–8192) и поднимать только если реально
не хватает контекста для промпта, проверяя `load_duration` в ответе Ollama (`total_duration`,
`load_duration` в JSON-ответе `/api/chat`) как сигнал — если `load_duration` внезапно вырос
на порядки при увеличении `num_ctx`, это и есть та самая ловушка.
