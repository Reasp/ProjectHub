При написании кросс-платформенного установщика (`scripts/lightrag/setup.mjs`), который сам
создаёт Python venv, оказалось, что на реальной пользовательской машине `python` в PATH
указывал не на системный Python, а на venv стороннего установленного приложения (в данном
случае — venv агента "Hermes", `...\hermes-agent\venv\Scripts\python.exe`), у которого вдобавок
был сломан pip ("No module named pip"). Слепой `python -m venv ...` на этом кандидате создал
бы venv поверх чужого/нерабочего интерпретатора вместо системного Python 3.13, который
физически стоял рядом, но не первым в PATH.

**Why:** на машинах разработчиков часто установлено несколько Python-подобных инструментов
(IDE, другие агенты, WindowsApps store-заглушки), и первый найденный в PATH — не обязательно
подходящий. Довериться этому вслепую в скрипте, который должен работать "на любой машине",
означало бы либо силентно сломать чужое приложение, либо упасть с непонятной ошибкой у
пользователя.

**How to apply:** при автонастройке Python-окружения — перебирать кандидатов в порядке
приоритета (на Windows: `py -3`, `python`, `python3`; на POSIX: `python3`, `python`), и для
каждого **проверять**, а не предполагать: (1) `--version` парсится и это Python >= нужной
версии, (2) `-m pip --version` реально работает (а не падает с "No module named pip"). Только
первый кандидат, прошедший обе проверки, использовать для `-m venv`. Никогда не переиспользовать
чужой venv стороннего приложения — создавать свой изолированный venv внутри своих скриптов.
Код: `findSystemPython()` в `F:\ProjectTemplate\scripts\lightrag\setup.mjs`.

настройки LightRAG на реальной машине.
