## Context

Цель проекта: управлять ADE с нескольких компьютеров. Сейчас Remote Control это телефон → один
ПК: локальный HTTP/WS-сервер, встроенный мобильный клиент, Telegram Mini App, Cloudflare Quick
Tunnel с меняющимся URL и релей-сервер без аутентификации. «Федерация» существует как модель
данных и три эндпоинта, но регистрация пиров ниоткуда не вызывается, список хостов всегда
содержит только себя, а ProjectHub не умеет быть клиентом другого ProjectHub. Режим WebRTC
объявлен в README и задаче, но `RTCPeerConnection` в коде отсутствует. Общий секретный ключ один
на все устройства, PIN брутфорсится без ограничений, Mini App шифрует пакеты в формате,
который хост не распознаёт.

Рассматривались: полноценный WebRTC P2P (сложная сигнализация, NAT, нет выигрыша для
двух-трёх ПК одного пользователя), VPN-подход (Tailscale/WireGuard, вне приложения),
собственный релей как каталог и транспорт.

## Decision

1. **Identity пользователя это ключевая пара** (Ed25519), создаваемая один раз и хранимая в
   `safeStorage`. Каждый хост (ПК с ProjectHub) и каждое устройство (телефон, Mini App, другой
   ПК) имеет свой ключ; доверие устанавливается сопряжением по QR или PIN один раз, после чего
   выдаётся per-device токен с правами (`readOnly`, `hitl`, `full`) и возможностью отзыва.
   Общий секрет на всех устройств отменяется.
2. **Транспорты: LAN Direct и Relay. WebRTC выводится из scope** и удаляется из документации
   до появления реальной потребности. Релей (`scripts/remote-relay-server.mjs`) становится
   каталогом хостов пользователя и транспортом: хост регистрируется подписью своего ключа,
   публикует метаданные (имя машины, платформа, версия, проекты, активные агенты, очередь HITL) и
   heartbeat; захват чужого `hostId` невозможен без ключа. Релей self-hosted: Dockerfile, TLS
   за reverse-proxy, документация деплоя. Cloudflare Quick Tunnel остаётся как быстрый
   fallback для Telegram.
3. **Единый формат E2EE-протокола** для всех клиентов: `{e2ee:true, iv, tag, data}` в hex,
   AES-256-GCM с ключом, выведенным из per-device секрета. Mini App использует общий
   `remoteCryptoWeb.ts`, а не собственную реализацию. Незашифрованные пакеты через релей не
   принимаются.
4. **Hub-режим.** Любой ProjectHub может подключиться к другому как клиент с правами своего
   устройства и показать его проекты, задачи, процессы, агентов и HITL-очередь в своём
   интерфейсе (отдельный узел в сайдбаре «Удалённые хосты»). RPC-набор един для телефона и
   ПК: всё, что объявлено в `RemoteRpcMethod`, реализовано в `dispatchRpc`, включая создание
   задачи, отправку промпта в AI Studio, запуск действий, старт агента с ролью и решения HITL по
   `requestId`.
5. **Назначение работы между машинами** делается через `assignee: agent:<role>@<hostId>`
   в задаче (см. [[decision-9]]): хост, увидев своё имя, запускает агента в своём worktree и
   публикует статус в федерацию. Очередь HITL и события агентов доступны с любого доверенного
   устройства.
6. **Офлайн и переподключение**: клиенты переподключаются с экспоненциальной задержкой, RPC
   имеют идемпотентные `requestId` и повтор, события, пропущенные во время разрыва, догоняются по
   `lastEventId`.

## Consequences

- Плюс: несколько ПК становятся одним рабочим пространством без VPN и ручного ввода адресов.
- Плюс: одна модель доступа для телефона, Telegram и другого ПК.
- Минус: нужен свой релей в интернете для работы вне LAN (self-hosted, документируется).
- Минус: отказ от WebRTC означает, что трафик вне LAN идёт через релей, но он зашифрован
  end-to-end и релей не видит содержимого.
- Реализация: ремонт текущего контура TASK-65, федерация TASK-66.

## Implementation note (TASK-65, 2026-09-11)

Пункты 1-3 и часть 6 реализованы в TASK-65: Ed25519-identity хоста (`node:crypto`, приватный
ключ — `secretStorageService`/`safeStorage`), per-device токены с правами
(`readOnly`/`hitl`/`full`) и отзывом, единый формат E2EE на всех клиентах (Mini App переведена на
общий `remote-crypto.js`), релей проверяет подпись хоста при регистрации и отклоняет захват
чужого `hostId` (`scripts/remote-relay-server.mjs`, `scripts/remoteRelayAuth.mjs`), Dockerfile и
инструкция self-hosted деплоя (`deploy/relay/`), экспоненциальный backoff на клиентах,
идемпотентность RPC по `requestId`, буфер событий для догона (`get_events_since`).

Дополнено в TASK-65 (2026-09-11, вторая итерация):

- Оба статических клиента (Telegram Mini App и встроенный веб-клиент) умеют подключаться к хосту
  **через релей**: сокет открывается к самому релею (`?role=client&hostId=...`), а PIN/ключ/токен
  предъявляются хосту отдельным зашифрованным пакетом `handshake` после `relay_ack`. Ответ
  `handshake_ack` теперь тоже шифруется, если запрос был зашифрован, — иначе per-device токен
  уезжал бы через чужой сервер открытым текстом.
- Live-события несут монотонный `eventId`, а `handshake_ack` — текущий `lastEventId`; клиенты
  запоминают последний увиденный id и после переподключения вызывают `get_events_since`, то есть
  догон событий работает end-to-end, а не только на стороне хоста.
- Права per-device токена назначаются точечно из UI (`remote:setDeviceRights`), в том числе
  устройствам не в сети; назначенные вручную права переживают пересопряжение по PIN.
- Каталог хостов на самом релее (`GET /api/federation/hosts`) закрыт токеном `RELAY_API_TOKEN`;
  пока токен не задан, каталог отключён, а не открыт анонимно.

## Implementation note (TASK-66, 2026-09-11)

Пункты 4-5 реализованы, решение переведено в `accepted`.

- **Каталог хостов на релее**: хост публикует метаданные и heartbeat (`host_meta_update` раз в
  30с) и получает каталог соседей (`catalog_request` / `catalog`) по уже аутентифицированному
  подписью сокету. Группировка машин одного пользователя — по `ownerId`, хэшу общего секрета
  федерации; чистые функции каталога вынесены в `scripts/remoteRelayCatalog.mjs`. Дополнительно
  работает LAN-обнаружение без релея (UDP-multicast, `lanDiscoveryService`). Подробности и
  отвергнутые альтернативы — [[decision-19]].
- **Hub-режим**: `federationClientService` открывает исходящие E2EE-соединения к другим
  ProjectHub (LAN напрямую или через релей), выполняет тот же набор RPC, что и телефон, и
  транслирует их события в рендерер. UI — узел «Удалённые хосты» в сайдбаре и модалка
  `RemoteHostsModal` (проекты, задачи, процессы, агенты и очередь HITL удалённой машины).
- **Единый RPC**: к существующему набору добавлены `get_roles`, `get_swarms`,
  `start_assigned_agent`, `stop_swarm`; права проверяются по per-device токену подключившегося
  ПК, как у любого другого устройства.
- **Назначение между машинами**: `assignee: agent:<role>@<hostId>` разбирается общим чистым
  модулем `src/utils/assignee.ts`; назначение на чужой хост маршрутизируется в `swarm:runAssigned`
  через hub-соединение, назначение на свой хост может запускаться автоматически backlog-вотчером
  (выключено по умолчанию, правила в `assignedTaskRules.ts`).
- **Версии и офлайн**: `handshake_ack` и `relay_ack` несут `protocolVersion`; несовпадение даёт
  понятное сообщение в UI и не рвёт транспорт для телефона, а офлайн-хост показывается статусом
  с автоматическим переподключением по экспоненциальному backoff.
