## Context

Приложение однокорневое: `selectedProject.path` указывает на основное рабочее дерево, и все
модули (Kanban, Git Inspector, File Explorer, AI Studio, Action Runner, процессы) работают с
ним. Worktree поддерживаются только точечно: терминал с `cwd` в worktree, панель worktree и
кнопка на карточке задачи. Идентификатор процесса это `projectPath::name`, поэтому два worktree
одного проекта конфликтуют по имени процесса и по порту dev-сервера. Заявленные «параллельные
ветки в одном проекте» на практике означают параллельные терминалы, а не параллельные
рабочие контексты.

## Decision

1. **Контекст приложения это пара «проект + рабочее дерево»** (`workspaceRoot`), а не только
   проект. Основное дерево это worktree по умолчанию. Переключатель активного worktree
   размещается рядом с именем проекта и в палитре команд; выбранный контекст сохраняется в
   состоянии окна.
2. **Модули читают контекст, а не `selectedProject.path`**: Git Inspector показывает ветку и
   дифф активного worktree, File Explorer и редактор открывают его файлы, AI Studio и агенты
   стартуют с `cwd` в нём, Action Runner и терминалы наследуют его. Backlog остаётся общим для
   всех worktree проекта (это одна и та же папка `backlog/` в основном дереве), но карточка
   задачи подсвечивает, в каком worktree над ней работают.
3. **Процессы изолируются по worktree**: идентификатор процесса включает `workspaceRoot`,
   профиль действия может задавать `portStrategy: fixed | auto`, при `auto` ProjectHub находит
   свободный порт и передаёт его через `PORT` и `${port}` в команде и `autoOpenUrl`. Занятые порты
   показываются в менеджере процессов с кнопкой освобождения.
4. **Ресурсы worktree, не входящие в git** (зависимости, `.env`), инициализируются по политике
   проекта в `.projecthub.json`: `worktreeInit` со списком команд (например `npm ci`) или
   символической ссылкой на `node_modules` основного дерева, если проект это допускает.
5. **Индикаторы параллельности**: сайдбар показывает число активных worktree и агентов в
   проекте; Kanban может группировать карточки по worktree; закрытие worktree ведёт в диалог
   завершения ([[decision-6]], [[decision-8]]).

## Реализация (TASK-62)

Решение реализовано; по ходу реализации уточнены три детали.

1. **Идентификатор процесса** — `${workspaceRoot}::${name}`, при этом `ManagedProcess.cwd`
   остаётся корнем проекта: процессы всех рабочих деревьев по-прежнему видны в одном списке
   проекта, но не схлопываются в одну запись. Выданные порты резервируются на время жизни
   процесса — иначе параллельный старт во втором worktree успевает получить тот же номер,
   пока первый сервер ещё не занял свой.
2. **Гард рабочего дерева** (`assertWorkspaceRoot`) признаёт worktree не по имени каталога
   `.worktrees/`, а по файлу `.git` с указателем `gitdir:` внутрь `<project>/.git/worktrees/`.
   Иначе любая подпапка проекта с подходящим именем принималась бы как рабочее дерево.
   Гард применён в IPC файлов и git-операций (TASK-32 разрешал только корень проекта).
3. **Выбор дерева хранится в localStorage рендерера** (`projecthub_active_worktrees`,
   карта «проект → worktree»), а не в `windowStateService`: тот отвечает только за геометрию
   окна, а все пользовательские выборы интерфейса (активная вкладка, фильтры, выбранный
   проект) уже живут в localStorage — выбор дерева относится к ним же.
4. **Backlog и контекст агента** остаются на корне проекта: `projectPath` в запросах агента —
   источник задач и документации, `workspaceRoot` — рабочий каталог CLI и инструментов
   записи файлов. Поэтому агент в worktree правит файлы своего дерева, но видит общий backlog.

## Consequences

- Плюс: настоящая параллельная работа над несколькими задачами и агентами в одном проекте с
  независимыми dev-серверами и диффами.
- Минус: рефакторинг стора: все места, использующие `selectedProject.path`, переводятся на
  `workspaceRoot`; на время миграции основное дерево остаётся значением по умолчанию, поэтому
  изменение обратно совместимо.
- Минус: дублирование зависимостей в worktree расходует диск и время; политика `worktreeInit`
  делает это явным выбором пользователя.
- Реализация: TASK-62 (после материализации результатов в TASK-55) — выполнена.
