## Context

Ревизия от 2026-09-10 ([[decision-4]], [[decision-9]]) зафиксировала три несвязанных дефекта
контекста агента (TASK-64):

- `aiAgentService.buildSystemPrompt` — четыре строки с рабочей директорией. Задача из
  Backlog.md, релевантные чанки `docs-rag` и связанный код в системный промпт не
  подставлялись; для AI Studio на Claude CLI (основной путь по [[decision-4]]) системного
  промпта не было вообще — только то, что неявно подхватывает сам `claude` из `cwd`
  (`CLAUDE.md`, `.mcp.json`). При этом Swarm/назначенные задачи уже несли контекст через
  `roleEngineAdapter.buildEngineInvocation`/`extraSystemPrompt` (TASK-60) — три движка кода,
  решающих одну и ту же задачу по-разному.
- Проектный `.mcp.json` не содержал `gitnexus`, хотя правила `CLAUDE.md` уже требуют
  `impact`/`explain` перед рефакторингом — агент не мог выполнить собственное правило.
- Связь задача → PR/worktree была односторонней: `gh pr create` переводил задачу в `Review`,
  но URL PR, имя ветки и путь worktree нигде не сохранялись; после перезапуска приложения
  их приходилось искать вручную по `git worktree list`/`gh pr list`.

Рассматривались альтернативы:

- **Контекст как MCP-клиент из main-процесса** (main сам ходит в `docs-rag`/GitNexus по
  протоколу MCP) — отклонено: `ragSearch.ts` уже даёт прямой TS-доступ к тому же индексу
  без протокола, а для GitNexus пришлось бы тащить в Electron клиент MCP и держать
  постоянное соединение с сервером ради разовых запросов на старте хода агента.
- **JSON-вывод GitNexus и его парсинг** — отклонено: у CLI (`gitnexus context`/`impact`,
  проверено `gitnexus --help`, 2026-09-11) нет флага структурированного вывода; получаемый
  человекочитаемый текст — это ровно то, что нужно системному промпту LLM, парсить незачем.
- **Файл `.projecthub/context/<taskId>.md` вместо `--append-system-prompt`** — отклонено как
  основной канал: у Claude CLI уже есть флаг, подтверждённый и используемый в TASK-60;
  добавление файла удвоило бы поверхность (два места с одним и тем же содержимым) без
  выигрыша, при этом файл слишком легко читать агенту как «источник правды сам по себе»
  вместо актуальной задачи.
- **Ветвление по движку в каждом месте вызова** (`if engine === 'claude-cli' ... else if ...`)
  — отклонено, прямо запрещено [[decision-4]] п.4: новая возможность обязана идти через общий
  адаптер, а не дублироваться по движкам.

## Decision

1. **`contextBuilder.buildAgentContext`** (`electron/services/contextBuilder.ts`) — единственное
   место, которое по `projectPath`/`taskId` собирает контекст: заголовок/описание/AC задачи
   (переиспользует `backlogTaskFormat.parseTaskBody`), топ-N чанков `ragSearch.searchProjectDocs`
   по тексту задачи, 360-обзор GitNexus по файлам из `references` задачи, git-статус (ветка +
   изменённые файлы). Каждый источник best-effort: любая ошибка (нет индекса RAG, GitNexus не
   проиндексирован или не установлен, задача не найдена) логируется и пропускает только свою
   часть, не прерывая сборку остального.
2. **Обрезка по бюджету — чистая функция `assembleContext`.** Приоритет частей фиксирован
   (`task > rag > gitnexus > git`); при нехватке `maxChars` (по умолчанию 6000) сначала
   обрезается текст внутри низкоприоритетной части, затем она отбрасывается целиком. Функция
   не трогает fs/сеть — покрыта unit-тестами без моков окружения.
3. **Единый канал — `extraSystemPrompt`, без ветвления по движку.** Результат
   `contextBuilder` не создаёт новый механизм доставки, а становится значением уже
   существующего параметра `roleEngineAdapter.buildEngineInvocation({ extraSystemPrompt })`
   (Swarm/назначенные задачи — через новый `agentFleetService.buildExtraSystemPrompt`,
   объединяющий `systemPromptAddon` слота с контекстом) и параметра `taskId` в
   `AIStreamRequest` (AI Studio на Claude CLI — `claudeBridgeService.runClaudeCliTask` теперь
   тоже собирает контекст и передаёт его через `--append-system-prompt`; AI Studio на
   API-движке — `aiAgentService.buildSystemPrompt`). Три движка, одна точка сборки.
4. **AI Studio привязывает сессию к задаче, а не подставляет контекст на каждое сообщение
   без разбора.** `AISession.activeTaskId` + `contextParts` (какие части включены) хранятся
   в сессии; quick-action «следующая задача» подбирает реальную задачу (`In Progress` или
   первая `To Do`) и привязывает её к сессии вместо статичного промпта. `ContextAppliedCard`
   показывает превью через новый IPC `ai:previewContext` (вызывает тот же `buildAgentContext`
   без запуска стрима) и позволяет выключать части на сессию. Ручные пилюли `@Task`/
   `@GitStatus`/`@Docs` не тронуты — это независимый путь ручной вставки текста в промпт.
5. **GitNexus — обычный CLI-процесс, не MCP-клиент в main.** `gitNexusClient.fetchGitNexusContext`
   вызывает `gitnexus context -f <file>` через `execFile` и берёт stdout как есть. GitNexus
   подключён в `.mcp.json`/`.agents/mcp_config.json` как MCP-сервер (`gitnexus mcp`) для
   агента-оболочки (Claude Code/Antigravity) — это отдельная роль от прямого вызова CLI из
   contextBuilder; фича `gitnexus` в `setup.mjs` включена по умолчанию, т.к. `CLAUDE.md`
   уже опирается на её наличие.
6. **`branch`/`worktree`/`pr` — обычные поля frontmatter задачи**, без отдельного файла
   состояния. `worktreeService.addWorktree` пишет `branch`/`worktree` сразу после создания
   worktree (по `extractTaskId` из имени ветки), `prService.syncBacklogOnPRCreated` — `pr`
   вместе с переводом в `Review`. Обе точки используют общий `taskFileLookup.findTaskFile`
   (вынесен из дублированной логики `prService`) и `normalizeFrontmatter`/`withUpdatedDate`
   из `backlogTaskFormat.ts` — во frontmatter не может попасть неэкранированный `Date`
   (правило 16 `infra-dev.md`). `TaskDetailModal` показывает поля как есть; `pr` — ссылка
   через `shell.openExternal`.

## Consequences

- Плюс: контекст задачи виден агенту одинаково, независимо от того, как он запущен (AI Studio,
  Swarm Fan-Out/Handoff, назначение через `assignee`) — один код, один набор источников.
- Плюс: добавление нового источника контекста в будущем (например, результатов автосудьи,
  [[decision-12]]) — это одно изменение в `contextBuilder`, а не правка трёх мест вызова.
- Плюс: worktree и PR больше не «теряются» после перезапуска — их видно прямо в карточке
  задачи без похода в `git worktree list`/`gh pr list`.
- Минус: GitNexus-часть контекста работает только если пользователь вручную проиндексировал
  репозиторий (`gitnexus analyze`) — до этого секция GitNexus молча отсутствует. Это
  осознанный компромисс (правило 7 `infra-dev.md`: не форсировать тяжёлые опциональные
  инструменты), но может создать впечатление, что фича не работает, если не подсказать
  пользователю про `gitnexus analyze`.
- Минус: превью контекста в `ContextAppliedCard` — снапшот на момент открытия карточки/смены
  переключателя, а не гарантированно то же самое, что уйдёт в промпт следующего сообщения
  (RAG/git-статус могут измениться между превью и отправкой). Для целей «что подставляется»
  этого достаточно, для точного аудита — нет.
- Долг: `gitNexusClient` не различает «репозиторий не проиндексирован», «бинарник не найден» и
  «символ не найден» — все ошибки схлопываются в пустой результат. Диагностика в UI (почему
  секция GitNexus пуста) не реализована в этой задаче.
- Реализация: TASK-64.
