## Context

Аудит doc-7 (п. 2.7) насчитал 26 вызовов `setTimeout` в компонентах, ни один из которых не
снимался при размонтировании. Схема везде одинаковая: `setCopied(true); setTimeout(() =>
setCopied(false), 2000)` или `setNotice(msg); setTimeout(() => setNotice(null), 4000)`. Побочные
эффекты: отложенный `setState` на уже размонтированном компоненте, «залипающие» уведомления
(модалку закрыли и открыли заново — старый таймер гасит новое сообщение), отложенный
`onClose()` модалки, срабатывающий после того, как её закрыли вручную.

Важно, что в React 19 предупреждение «Can't perform a React state update on an unmounted
component» удалено из рантайма (убрано ещё в React 18). Значит, проверять корректность «по
отсутствию варнинга в консоли» больше нельзя — гарантию должна давать сама конструкция кода,
а не наблюдение за консолью.

Рассмотренные варианты:

- Оставить ручной `useEffect` с `clearTimeout` в каждом месте — это и есть текущее состояние:
  из 26 мест правильно сделаны единицы, а каждое новое уведомление повторяет ошибку заново.
- Взять готовую библиотеку тостов — лишняя зависимость и чужая разметка ради логики в 40 строк;
  уведомления в проекте разные по виду (строка в шапке панели, бейдж «скопировано», плавающий тост).
- Общий хук поверх маленького чистого реестра таймеров — логика учёта покрывается unit-тестами
  без React-окружения (в проекте нет jsdom и testing-library, и добавлять их ради этого не нужно).

## Decision

1. Учёт таймеров живёт в чистом классе `TimerRegistry` (`src/lib/timerRegistry.ts`) — без React и
   Electron: `set`/`clear`/`clearAll`/`dispose`, после `dispose()` новые таймеры не создаются и
   уже сработавшие колбэки не выполняются. Он и покрыт тестами (`tests/unit/timerRegistry.test.ts`).
2. Компоненты используют хуки из `src/hooks/useTimeoutState.ts`:
   - `useTimeoutState(resetValue, delayMs)` — состояние, которое само возвращается к
     `resetValue`; возвращает `[value, show, reset]`.
   - `useToast<T>(delayMs)` — частный случай с `null` по умолчанию.
   - `useTimers()` — `setTimer`/`clearTimer`/`clearTimers` для отложенных действий, не сводящихся
     к сбросу состояния: фокус поля, `fit()` у xterm, отложенное закрытие модалки.
3. Прямой `setTimeout` в компоненте допустим только в двух случаях: он создаётся внутри
   `useEffect`, который снимает его в своём cleanup (дебаунс, поллинг), либо это `await new
   Promise(r => setTimeout(r, ms))` внутри async-потока. Во всех остальных местах — хук.
4. `show` и `setTimer` стабильны между рендерами, поэтому их можно и нужно указывать в массивах
   зависимостей `useEffect` — новых предупреждений `react-hooks/exhaustive-deps` это не создаёт.
5. Корректность проверяется структурно (таймер зарегистрирован в реестре компонента) и тестами
   реестра, а не поиском предупреждения React в консоли — такого предупреждения больше нет.

## Consequences

**Плюсы.** Уведомление не может пережить свой компонент и не может быть погашено таймером от
предыдущего показа: новый `show` снимает предыдущий таймер. Места, где раньше дублировалась пара
«состояние + таймер», стали на 4–5 строк короче каждое. `VoiceControlWidget`, который вёл
собственный `timersRef`, перешёл на общий хук — свой механизм удалён.

**Минусы и долг.** Хук привязывает жизнь таймера к компоненту: если уведомление должно пережить
размонтирование (например, глобальный тост из стора), хук не подходит — такие случаи нужно
класть в стор. `useTimers` в строгом режиме React пересоздаёт реестр после двойного монтирования —
это учтено в хуке, но делает его чуть менее очевидным, чем обёртка в одну строку.

из [[decision-17]] решение не затрагивает: там про `createPortal` и шкалу `z-index`, здесь про таймеры.
