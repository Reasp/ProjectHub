## Context

`useProjectStore` — единый глобальный стор рендерера: он одновременно держит список проектов
(глобальное состояние) и данные **одного** выбранного проекта — задачи, git-логи и детали
репозитория, документы, майлстоуны, процессы, PR, фильтры задач. Переключение проектов при этом
асинхронное: `selectProject` менял только `selectedProject`, а остальные поля перезаписывались
лишь когда возвращались IPC-ответы (`getTasks`, `getGitLog`, `listDocs`, `listMilestones`,
`listProcesses`).

Из-за этого между кликом по проекту и приходом данных на экране оставался предыдущий проект:
пользователь видел в канбане чужие задачи и считал, что переключение не сработало. Эффект
проявлялся только на проектах, которых ещё нет в `projectDataCache` (см. кэш мгновенного
переключения, TASK-38) — то есть при первом открытии проекта в сессии, где ожидание самое
заметное.

Второй, более редкий, но того же класса дефект — гонка ответов: `fetchDocs`, `fetchMilestones`,
`fetchProcesses`, `fetchPRs`, `fetchPRProviderInfo` и `loadGitRepoDetails` писали результат в стор
без проверки, тот ли проект всё ещё выбран. При быстром переключении A → B поздний ответ по A
затирал данные B. В `loadActionConfig` такая проверка уже была — практика существовала, но нигде
не была записана и потому не применялась последовательно.

Рассмотренные альтернативы:

1. **Хранить данные по ключу проекта** (`Record<projectPath, ProjectData>`) и селектором отдавать
   срез выбранного проекта. Радикально убирает и устаревшие данные, и гонки, но это переписывание
   всего стора и всех компонентов; частично эту роль уже играет `projectDataCache`.
2. **Спиннер поверх старых данных без сброса.** Дёшево, но пользователь всё равно видит чужие
   задачи под полупрозрачным слоем, а локальное состояние вью (открытая карточка задачи) остаётся
   от прошлого проекта.
3. **Синхронный сброс проектного состояния + индикатор + отбрасывание поздних ответов** — выбрано.

## Decision

1. **Проектное состояние стора выделено в одну функцию** `emptyProjectScopedState()`
   (`src/store/useProjectStore.ts`). Она перечисляет все поля, принадлежащие конкретному проекту,
   и возвращает их «нулевые» значения. Любое новое проектное поле стора обязано добавляться в неё —
   иначе оно переживёт смену проекта. Контракт закреплён юнит-тестом
   `tests/unit/projectScopedState.test.ts`.
2. **Смена проекта сбрасывает это состояние синхронно**, до любого IPC: в `selectProject` (при
   переходе на другой проект и при `selectProject(null)`) и в `deactivateProject`. Фильтры задач по
   метке и майлстоуну считаются проектными (их id в другом проекте не существуют) и чистятся вместе
   с персистентными ключами в `localStorage`.
3. **Флаг `isProjectDataLoading`** выставляется, только когда данных проекта нет в
   `projectDataCache`; `loadProjectData` снимает его в `finally` и лишь если проект всё ещё выбран.
   В кэшированной ветке индикатор не показывается — переключение остаётся мгновенным.
4. **Все асинхронные загрузчики проектных данных проверяют актуальность проекта после `await`** и
   молча отбрасывают ответ, если пользователь уже ушёл на другой проект. Сравнение путей — через
   `samePath` (регистр и разделители на Windows).
5. **Контейнер вкладок рабочей области монтируется с `key={selectedProject?.path}`**
   (`ProjectWorkspace`): при смене проекта вью перемонтируются, и локальное состояние компонентов
   (строка поиска задач, открытая карточка `TaskDetailModal`, выбранный файл диффа, дерево файлов)
   не переносится между проектами.
6. **Индикатор загрузки — локальный оверлей** внутри `relative`-контейнера рабочей области с
   `z-20`. Это не модальное окно, шкала `z-index` для модалок из [[decision-17]] на него не
   распространяется и не нарушается.

## Consequences

**Плюсы**

- Переключение проекта больше не показывает данные предыдущего: либо мгновенно правильные данные
  из кэша, либо индикатор загрузки.
- Гонки «поздний ответ по старому проекту» закрыты единообразно во всех загрузчиках.
- Один список проектных полей вместо трёх разных наборов сброса, разъехавшихся по коду.

**Минусы и долг**

- Стор по-прежнему хранит данные одного проекта плоскими полями; альтернатива 1 (данные по ключу
  проекта) остаётся более чистым решением и может понадобиться, если появятся вью, показывающие
  несколько проектов одновременно.
- Перемонтирование по `key` сбрасывает локальное состояние всех вкладок, включая полезное
  (позиция скролла). Это осознанный размен в пользу отсутствия чужого контекста.
- `emptyProjectScopedState()` нужно поддерживать вручную при добавлении проектных полей; страховка —
  юнит-тест со списком ключей, который упадёт при рассинхроне только если ключ добавили в тест.

Реализация: TASK-67.
