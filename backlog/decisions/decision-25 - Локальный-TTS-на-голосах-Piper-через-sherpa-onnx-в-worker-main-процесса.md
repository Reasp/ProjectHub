## Context

Озвучка в ProjectHub сейчас — `window.speechSynthesis` в рендерере (`voiceService.speak`):
системные голоса SAPI/macOS, без выбора устройства вывода (в приложении уже есть выбор
`audioOutputDeviceId` для VAD/плеера, но `speechSynthesis` его игнорирует), качество русских
системных голосов на Windows низкое, а на машинах без установленного русского голоса озвучки нет
вовсе. TASK-69 запрашивает локальный нейросетевой движок с кастомизацией и импортом собственных
голосов.

Что выяснено при исследовании 2026-09-15:

- **Piper сменил дом и лицензию.** `rhasspy/piper` (MIT) заархивирован в октябре 2025; развитие
  ведёт Open Home Foundation в `OHF-Voice/piper1-gpl` под **GPL-3.0** — причина в встроенном
  фонемизаторе espeak-ng (сам GPL-3). Python-пакет `piper-tts` 1.6.0 (июль 2026). Node-биндинга
  у Piper нет, есть только Python, C/C++ и HTTP-сервер.
- **Голоса — отдельный артефакт.** `rhasspy/piper-voices` (Hugging Face, репозиторий MIT).
  Русские: `ru_RU-irina`, `ru_RU-dmitri`, `ru_RU-denis`, `ru_RU-ruslan`, все `medium`
  (22050 Гц), обучены на данных RHVoice; лицензия датасета в MODEL_CARD указана как «Unknown».
  Для личного local-first использования это приемлемо, для публичного распространения бинарника
  с голосами — нет, поэтому голоса в бандл не включаются и скачиваются пользователем.
- **Kokoro-82M** (лидер по качеству на CPU в 2026, Apache-2.0) не поддерживает русский —
  не годится как основной движок; возможен как дополнительный для английского позже.
- **Рантаймы для Node/Electron:**
  - A. `sherpa-onnx-node` 1.13.8 (k2-fsa, Apache-2.0): prebuilt нативные библиотеки через
    `optionalDependencies` (`sherpa-onnx-win-x64`, `-linux-x64`, `-darwin-arm64` и др.),
    встроенный espeak-ng, готовые конвертированные архивы всех Piper-голосов в релизах
    `tts-models` + общий `espeak-ng-data`. Пользовательские `.onnx + .onnx.json` требуют
    конвертации: `tokens.txt` из `phoneme_id_map` и metadata (`model_type`, `comment=piper`,
    `sample_rate`, `n_speakers`, `voice`) в ONNX.
  - B. `onnxruntime-web` + piper-phonemize WASM в рендерере (`@mintplex-labs/piper-tts-web`
    1.0.5, `@diffusionstudio/vits-web` 1.0.3, MIT): без нативных зависимостей, голоса с HF без
    конвертации, но WASM-инференс медленнее, ассеты по умолчанию тянутся с CDN, а архитектурно
    это второй способ выполнять тяжёлые вычисления (в рендерере), противоречащий [[decision-21]].
  - C. `onnxruntime-node` (уже в дереве зависимостей через `@huggingface/transformers`) с
    собственной фонемизацией: готового Node-фонемизатора espeak-ng нет, писать свой — нереально.
  Отвергнутая альтернатива: ставить Python `piper-tts` и дергать как процесс — тянет Python-рантайм
  в десктоп-приложение, как LightRAG, который сознательно сделан опциональным.

## Decision

1. **Движок TTS — Piper-голоса (VITS/ONNX) через `sherpa-onnx-node`**, выполняемый в
   `worker_threads` main-процесса по образцу `whisperWorker` ([[decision-21]]): ленивая загрузка,
   очередь заданий, таймаут, ограниченный respawn, in-process fallback.
2. **Системный `speechSynthesis` остаётся** как движок по умолчанию и как деградация при
   отсутствии модели, ошибке воркера или недоступном нативном модуле. Приложение не падает.
3. **Голоса скачиваются в `<userData>/models/tts/<voiceId>/`** из релизов sherpa-onnx с проверкой
   sha256; встроенный реестр: ru ×4 и en ×2. В бандл приложения модели не входят (размер и
   лицензия датасета).
4. **Импорт пользовательского голоса** — стандартная пара Piper `.onnx + .onnx.json`, конвертация
   в формат sherpa выполняется в JS внутри приложения (без Python).
5. **Воспроизведение — в рендерере** через `AudioContext` с `setSinkId(audioOutputDeviceId)`:
   main отдаёт PCM-чанки по предложениям через IPC, первый чанк должен звучать до 1 с.
   `stop_reading` отменяет и генерацию (по `jobId`), и воспроизведение; на время речи VAD глушится.
6. **Лицензионная заметка** фиксируется в этом ADR: код Piper (GPL-3) не используется, но
   espeak-ng внутри sherpa-onnx — GPL-3-компонент; при любом публичном распространении бинарника
   это нужно отразить в лицензионных уведомлениях.
7. **Запасной план:** если prebuilt `sherpa-onnx-node` не загружается из упакованного Electron
   (`asarUnpack`) — переход на вариант B в рендерере с self-hosted WASM/ассетами; ADR обновляется.

## Consequences

- Плюс: естественная русская озвучка полностью оффлайн на CPU, ~50–80 МБ на голос в памяти,
  выбор устройства вывода, единая схема изоляции тяжёлых вычислений с Whisper и RAG.
- Плюс: пользовательские голоса без Python и без пересборки приложения.
- Минус: новая нативная зависимость с платформенными пакетами — `external` в `vite.config.ts`,
  `asarUnpack`, проверка `check-bundle`; CI на трёх ОС (decision-14) должен ставить
  соответствующий `optionalDependency`.
- Минус: конвертация пользовательских голосов — собственный код (metadata в ONNX через protobuf);
  если sherpa примет модель без metadata, шаг упрощается — проверить в спайке.
- Долг: качество Piper-голосов «medium» заметно синтетичнее Kokoro/XTTS; расширение на другие
  движки (Kokoro для en) — отдельная задача при спросе.
- Реализация: TASK-69. Статус ADR переводится в `accepted` после замеров (RTF, память, время
  загрузки) в упакованном приложении.
