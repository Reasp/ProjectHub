## Context

`executeSubprocess` (`claudeBridgeService.ts`) запускает команды агента через `powershell.exe -Command`
и завершал промис только по событию `close`. Оно приходит, когда закрыты **все** копии stdio-каналов,
включая унаследованные потомками. Остановка (`abortSession`, таймаут) шла через `killProcessTree` →
`tree-kill`, на Windows это `taskkill /T /F` по снимку дерева процессов.

Инструментированный прогон полного `npm test` (TASK-97, 2026-09-18) подтвердил сценарий зависания.
Тест «abortSession убивает команды агента этой сессии» делает abort через 300 мс после запуска, пока
PowerShell ещё стартует. В двух прогонах из четырёх:

- `exit` оболочки пришёл через 0,5–1 с после abort, `close` не пришёл вообще;
- внук `node.exe` (PID 43144 и 24252) был создан PowerShell уже после снимка `taskkill` и жил дальше
  с ParentProcessId мёртвой оболочки, держа stdout;
- промис висел до таймаута теста (15 с). Таймер `executeSubprocess` не помогал: `killProcessTree`
  сразу выходит, если `exitCode !== null`.

Сироты переживали и сам vitest: на машине нашлись 26 таких процессов `node -e "setInterval…"` с 15.09.
В продукте то же самое означало вечное ожидание прерванной команды агента и утечку процессов.

Рассмотренные варианты:

1. **Job Object на Windows** (все потомки в задании с `KILL_ON_JOB_CLOSE`). Ловит любые цепочки,
   включая «внук от уже умершего промежуточного процесса». Но в Node нет API для Job Object: нужен
   нативный аддон (ещё одна нативная зависимость для `electron-builder`) или обёртка команды в
   PowerShell с `Add-Type` и P/Invoke. Второй вариант компилирует C# при каждом запуске команды
   (+1–2 с к каждой команде агента) и меняет то, что видит пользователь в команде. Отложено.
2. **Повторный `tree-kill` по сохранённому PID.** Не работает: `taskkill /T` требует живой корень,
   а к моменту повтора оболочка уже мертва.
3. **Добивание по цепочке ParentProcessId из снимка процессов после выхода оболочки.** Выбрано:
   без новых зависимостей, стоимость — один запрос `Get-CimInstance Win32_Process` только при
   abort или таймауте.

Отдельно выяснилось: libuv на Windows сам кладёт прямых потомков node-процесса в Job Object с
`KILL_ON_JOB_CLOSE` (если не `detached`), но с `SILENT_BREAKAWAY_OK`. Поэтому PowerShell умирает
вместе с ProjectHub, а его потомки — нет.

## Decision

1. **Промис `executeSubprocess` завершается по `exit` оболочки** с ограниченным ожиданием `close`:
   `SUBPROCESS_CLOSE_GRACE_MS` = 1500 мс. Если `close` не пришёл, stdio-потоки уничтожаются
   (`destroy()`), и промис резолвится с кодом из `exit`. Это верно и для обычного выхода: фоновый
   процесс, который держит stdio, больше не вешает команду.
2. **После abort или таймаута пережившие потомки добиваются** модулем `processSweep.ts`. Снимок
   `Win32_Process` (pid, ppid, время создания) и обход в ширину от PID оболочки, которая сама может
   отсутствовать в снимке. Найденные процессы убиваются через `tree-kill`. Ожидание `close`
   начинается после добивания.
3. **Защита от переиспользования PID:** потомок учитывается, только если он создан не раньше
   родителя (корень — отметка `Date.now()` перед `spawn`) с допуском 2 с.
4. **Без abort или таймаута потомков не трогаем:** фоновый процесс, запущенный командой, мог быть
   намеренным. Промис только перестаёт его ждать.
5. **`killProcessTree` не меняется:** его используют `runClaudeCliTask`, `killAll` и
   `performGracefulShutdown` (GitNexus impact: риск HIGH). Добивание подключается через
   собственный kill-обработчик команды, который `killSessionProcesses` вызывает вместо
   `killProcessTree`.
6. **Только Windows.** На POSIX осиротевший процесс переподчиняется init, и по ppid его не найти.
   Там остаётся гарантия п. 1: промис завершается за ограниченное время.

## Consequences

- Прерванная или просроченная команда агента завершается не позже чем через
  `SUBPROCESS_CLOSE_GRACE_MS` после выхода оболочки плюс время снимка процессов (обычно около 1 с),
  а не висит бесконечно.
- Сироты, появившиеся в гонке со снимком `taskkill`, не остаются.
- Ограничение: цепочка через уже умерший промежуточный процесс (оболочка → A → B, где A вышел до
  abort) по ParentProcessId не находится. Промис всё равно завершается (п. 1), но B может остаться.
  Полное решение — Job Object (вариант 1 в Context), если такие случаи появятся на практике.
- Реализация и тесты: TASK-97 (`tests/unit/processSweep.test.ts`,
  `tests/unit/executeSubprocessOrphans.test.ts`).

## Дополнение: CLI-агенты Swarm и Handoff (TASK-99, 2026-09-18)

`agentFleetService` запускал агентов (`claude`, `codex.cmd`, `gemini.cmd`) через `spawn(..., { shell: true })`,
то есть корнем был `cmd.exe`, а движок — его потомком. Завершение шло только по `close`, остановка — через
собственный `killProcessTree` (tree-kill). Тест с подменённым tree-kill («убить только этот PID») подтвердил
зависание всех трёх путей навсегда: и при остановке, и при обычном выходе, если stdio держит фоновый потомок.

1. **Логика п. 1–4 вынесена в общий хелпер** `superviseChildExit` (`processSweep.ts`): ожидание `close` не
   дольше `CHILD_CLOSE_GRACE_MS` после `exit`, уничтожение потоков, `kill()` — tree-kill живого процесса или
   добивание потомков уже вышедшего, ожидание после добивания. `executeSubprocess` переведён на него
   (`SUBPROCESS_CLOSE_GRACE_MS` = `CHILD_CLOSE_GRACE_MS`), поведение прежнее.
2. **В `agentFleetService` все три CLI-пути** завершаются через хелпер вместо `close`. Все точки остановки
   (`killAgentProcess`, `stopSwarm`, `killAll`, лимит ходов роли, ошибка записи промпта) идут через
   `stopAgentChild`: для процесса под надзором — его `kill()`, иначе прежний `killProcessTree`.
3. **`killProcessTree` в `agentFleetService` не меняется** (GitNexus impact: CRITICAL, 23 зависимых, включая
   `performGracefulShutdown`): он остаётся «сырым» tree-kill, который хелпер вызывает для живого процесса.
   Добивание при остановке через `killAll` на выходе из приложения — best effort: процесс может завершиться
   раньше снимка.

Проверка с настоящим tree-kill (30 прогонов, остановка через 0–300 мс после запуска, цепочка
`cmd.exe` → `node`) сирот не дала: node стартует раньше, чем `taskkill` делает снимок. Риск в продукте
остаётся для потомков, которые движок порождает в момент остановки (инструменты, MCP-серверы), и для
фоновых процессов с унаследованным stdio. Как нативный `claude.exe` порождает потомков, не проверялось.
