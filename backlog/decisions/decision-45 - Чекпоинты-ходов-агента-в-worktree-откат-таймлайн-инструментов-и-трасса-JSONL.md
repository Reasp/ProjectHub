## Context

До TASK-72 результат агента фиксировался в git только в конце хода: `materializeAgentResult` делает `git add -A` и
коммит (или `git stash create` при выключенном авто-коммите, [[decision-8]]). Промежуточных состояний не было, поэтому
откатить агента к середине работы было нельзя. Лог слота хранил строки `[Tool] имя` без длительности, статуса и
стоимости, а транскрипт — сырой вывод ([[decision-16]]). Что агент делал, сколько это заняло и стоило, из UI не
восстанавливалось.

Проверено вживую 2026-09-19:

- **Claude CLI 2.1.275** (`claude -p --model haiku --output-format stream-json --verbose`, чтение и запись файла):
  - поле `timestamp` (ISO) есть у событий `assistant` и `user`; у `system`, `rate_limit_event` и `result` его нет;
  - одно сообщение модели приходит несколькими событиями `assistant` с общим `message.id` (блок `thinking`, затем
    `tool_use` или `text`), и в каждом повторяется одинаковый `usage`;
  - `output_tokens` в этих событиях частичный (1–4 токена против 439 в `result`), вход и кэш — точные;
  - результат инструмента приходит событием `user` с блоком `tool_result` (`tool_use_id`, `content`, `is_error`) и
    полем `tool_use_result`;
  - длительность инструмента = `user.timestamp − assistant(tool_use).timestamp`: 85 мс у Read, 60 мс у Write;
  - `result` даёт `duration_ms`, `num_turns`, итоговый `usage` и `total_cost_usd`.
- **Сервис флота** складывал `usage` каждого события `assistant` (`recordUsage(..., 'add')`). Сообщение из двух
  событий считалось дважды, и бюджет слота мог сработать раньше времени. Итог `result` затирал ошибку, но проверка
  бюджета внутри хода видела завышенную сумму.
- **API-движок Swarm** (`runApiAgent`) вызывает `aiAgentService.streamChat` без `executeTool`. Модель получает
  описания инструментов, но Swarm их не исполняет: вызов только пишется в лог. Tool-loop с исполнением есть только в
  AI Studio (`claudeBridgeService`, TASK-82). Границ исполнения инструмента в чанках `streamChat` не было.
- **Снимок через временный индекс** (git 2.x, worktree, `core.autocrlf=false`). Во временный файл копируется индекс
  worktree (`git rev-parse --git-path index`), затем `GIT_INDEX_FILE=<tmp> git add -A`, `write-tree` и
  `commit-tree <tree> -p HEAD`, а ref ставится через `update-ref`. Что показала проверка:
  - в снимок попали изменённый, новый неотслеживаемый и staged файлы, удалённый файл не попал;
  - `.gitignore` соблюдён: `ignored.log` и `node_modules/` не вошли;
  - HEAD, файл индекса (sha1) и `git status --porcelain -uall` worktree до и после совпали;
  - `git log` ветки чекпоинт не содержит, а `for-each-ref refs/projecthub` из основного репозитория видит оба ref:
    refs общие для всех worktree.
  - Для сравнения: `git stash create` новый неотслеживаемый файл не взял.
- **Откат**, проверенный на том же worktree после ещё одного авто-коммита и грязного файла, выполняется пятью
  командами:
  1. `reset --hard <родитель снимка>`;
  2. `checkout <снимок> -- .`;
  3. удаление файлов из `diff --name-only --diff-filter=D <родитель> <снимок>`;
  4. удаление файлов из `ls-files --others --exclude-standard`;
  5. `reset` (mixed).

  Дерево рабочего каталога совпало с деревом снимка, игнорируемые файлы остались на месте, а снимок «перед откатом»
  сохранил отменённую работу.

Рассмотренные и отвергнутые варианты:

1. **Коммит в ветку слота на каждом ходе** (исходное описание задачи). Отвергнут: засоряет историю ветки победителя и
   двигает HEAD, пока агент работает (гонка с его собственными git-командами). Вдобавок требует squash при слиянии,
   а [[decision-8]] сливает через `--no-ff`.
2. **`git stash create` + ref.** Отвергнут: снимок не берёт неотслеживаемые файлы, а агент создаёт именно их.
3. **Служебная ветка на слот.** Отвергнута: ветка видна в `git branch` и в сборщике мусора `swarm/*`, а коммит в неё
   без смены HEAD — тот же `commit-tree`, только с лишней сущностью.
4. **Отдельный репозиторий или копии файлов** (так делает Claude Code в `~/.claude/file-history`). Отвергнут: объекты
   дублируются, копия не чистится вместе с worktree и работает только для одного движка.
5. **Откат в основном дереве проекта** (`useWorktrees: false`). Отвергнут: там же работает человек, и
   `reset --hard` с удалением неотслеживаемых файлов уничтожил бы его правки.
6. **Трасса внутри JSON сессии.** Отвергнута: сессия целиком уходит в рендерер на каждый чанк и пишется на диск раз в
   секунду ([[decision-16]]), а трасса растёт с числом вызовов инструментов.

## Decision

1. **Формат чекпоинта.** Чекпоинт — коммит-объект вне истории ветки: снимок рабочего дерева через временный индекс и
   `commit-tree` с родителем HEAD, ref `refs/projecthub/checkpoints/<swarmId>/<agentId>/<n>`.
   - Автор коммита — `ProjectHub Checkpoint <agent@projecthub.local>`, сообщение — `checkpoint(<agentId>): <вид> #<n>`.
   - Временный индекс — копия индекса worktree в `os.tmpdir()`. Копия сохраняет кэш stat, поэтому `add -A` идёт
     инкрементально. После снимка файл удаляется. Индекс и HEAD worktree не трогаются никогда, агент может работать
     параллельно.
   - Если дерево совпадает с деревом предыдущего чекпоинта агента, новый не создаётся: ход ссылается на прежний.
   - Виды чекпоинтов: `start` (перед запуском хода движка), `turn` (после инструментов хода), `end` (после хода
     движка, до авто-коммита) и `pre_rewind` (перед откатом).
   - Логика git — чистый модуль `checkpointGit.ts` без Electron (`git` через `execFile`). Очередь операций по агенту и
     лимиты — `checkpointService.ts`. В сессии хранится список `AgentSlotState.checkpoints` (номер, вид, ход, коммит,
     дерево, родитель, число изменённых файлов, время).
2. **Где разрешены.** Чекпоинты создаются везде, где рабочий каталог агента — git-репозиторий, в том числе в основном
   дереве проекта при `useWorktrees: false` или неудачном создании worktree: это только объекты и ref, файлы не
   меняются. Откат разрешён только в worktree слота. Дополнительные условия:
   - агент и сессия не активны;
   - агент не победитель, уже влитый в базовую ветку;
   - worktree есть на диске.

   Вне git чекпоинты молча выключены, в лог слота пишется одна строка.
3. **Что такое «ход».**
   - **Claude CLI**: ход — одно сообщение модели, то есть события `assistant` с общим `message.id`, склеенные в одно.
     Чекпоинт `turn` снимается, когда пришли результаты всех `tool_use` этого сообщения. Сообщение без инструментов
     чекпоинта не даёт: файлы меняют только инструменты.
   - **API-движок**: ход — один запрос к модели (шаг tool-loop). В Swarm сейчас один запрос на запуск, инструменты не
     исполняются, поэтому таймлайн показывает их как «не исполнен», а чекпоинты — `start` и `end`. Границы исполнения
     инструмента добавлены в `streamChat` без смены сигнатуры: чанк `step` в начале каждого запроса к модели и чанк
     `toolResult` (id, имя, успех, размер вывода, длительность) после исполнения. Ими пользуется таймлайн, когда
     исполнитель есть.
   - **Цикл «до готовности»** ([[decision-28]]): итерация — это запуск движка (`run`). Перед ним снимается `start`,
     после — `end`, а внутри — `turn` по правилам движка.
   - **Codex и Gemini CLI**: только `start` и `end` на запуск, в таймлайне — запуск без инструментов (до TASK-71).
   - Номера ходов и запусков сквозные на всё время жизни агента: переживают итерации цикла, продолжение после отката и
     перезапуск приложения (счётчики в `AgentSlotState.trace`).
4. **Откат** (`swarm:rewind`, подтверждение через DialogHost `z-[10001]`, [[decision-17]]).
   1. Снимается чекпоинт `pre_rewind` текущего состояния. Отменённая работа не теряется: к нему можно откатиться так
      же, это «отмена отката».
   2. Выполняются шаги, проверенные вживую:
      - `reset --hard` на родителя снимка — ветка возвращается к коммиту, который был HEAD в момент снимка;
      - `checkout <снимок> -- .`;
      - удаление файлов, удалённых в снимке относительно родителя;
      - удаление неотслеживаемых неигнорируемых файлов по списку (`ls-files --others --exclude-standard`, не
        `clean -fdx`);
      - `reset` (mixed).
   3. Откатанное состояние сразу фиксируется `materializeAgentResult` с сообщением
      `rewind(<роль>): чекпоинт #<n> (после хода <T>)`. Pick Winner сливает коммиты, и без этого шага слилась бы отменённая
      работа.
   4. Дифф с базовой веткой пересчитывается.
   5. Агент получает запись `rewinds[]`: куда откатились, какой снимок сохранил прежнее состояние, когда, сколько
      файлов удалено. «Удалено» считается относительно состояния до отката (дифф деревьев `pre_rewind` → снимок):
      часть файлов убирает уже `reset --hard`, поэтому список команд отката для этого не годится. Карточка
      показывает бейдж «откат к #N», трасса — событие `rewind`, Markdown-экспорт — строку об откате.
   6. `cliSessionId` и история API-диалога сбрасываются. Следующий запуск агента начинается с новой сессии: Claude CLI
      без `--resume`, API с пустой историей. В промпт добавляется пояснение «рабочий каталог откатён к состоянию
      после хода N, последующие изменения отменены, изучи текущее состояние файлов и продолжи».
   7. Продолжить после отката можно кнопкой «Продолжить агента» (`swarm:continueAgent`) в сессиях fan-out, в том
      числе назначенных. Можно дописать уточнение. Usage нового запуска складывается с прежними запусками
      через ту же базу, что и у цикла «до готовности» ([[decision-28]] п. 6). Без базы итог `result` затёр бы
      стоимость первого запуска — это показала живая проверка. В handoff и цикле «до готовности» ходом управляет
      контроллер сессии, поэтому откат там только меняет файлы, а продолжения из карточки нет (долг).
5. **Судьба ref.**
   - Ref удаляются вместе с worktree: `discardSwarm` удаляет весь префикс `refs/projecthub/checkpoints/<swarmId>/`,
     Pick Winner — ref проигравших после удаления их worktree.
   - Ref победителя живут, пока живёт его worktree, то есть до закрытия сессии, как в [[decision-16]].
   - При восстановлении сессий после старта удаляются ref сессий, которых больше нет на диске.
   - Лимит — 50 чекпоинтов на агента. При превышении удаляется самый старый ref, запись о нём остаётся в трассе.
     Недостижимые коммиты убирает обычный `git gc`.
   - В ветку победителя чекпоинты не попадают никогда: она содержит только авто-коммиты [[decision-8]].
6. **Трасса.** `<userData>/swarms/<swarmId>/<agentId>.trace.jsonl`, одна строка — одно событие. Запись идёт
   очередью рядом с транскриптом. При 5 МБ файл ротируется в `.trace.1.jsonl`, а удаляется вместе с каталогом сессии.
   - Общие поля события: `v: 1`, `type`, `at` (мс), `run`, `turn` (если есть).
   - Типы событий: `run_start`, `turn_start`, `tool_call` (имя, аргументы до 300 символов), `tool_result` (успех,
     размер вывода, длительность), `hitl`, `model_switch` ([[decision-44]]), `usage`, `checkpoint`, `rewind`, `error`,
     `run_end`.
   - Время событий Claude CLI берётся из `timestamp` события, иначе — время приёма строки.
   - `hitl` берётся из шины (`hitl:requested/decided/expired/cancelled`) по `sessionId` агента. Авто-решения политики
     [[decision-10]] приходят локальным событием `hitlService` `autoDecided`: в шину их не публикуем, чтобы не
     порождать уведомления.
   - `usage`:
     - Claude CLI: на ход — по первому событию сообщения. Вход и кэш точные, выход помечен `partial: true`, поэтому
       стоимость хода — оценка.
     - Итог запуска — по `result` или usage API ([[decision-42]]).
   - `error` несёт вид ошибки провайдера ([[decision-43]]).
   - Разбор событий движков и сборка таймлайна (ходы, инструменты, длительности, статусы, стоимость) — чистый модуль
     `agentTrace.ts` с unit-тестами. Рендерер получает готовый таймлайн через `swarm:getTimeline`.
   - Экспорт `swarm:exportTrace` пишет JSONL. Первая строка — `type: "header"`, `format: "projecthub-agent-trace"`,
     `v: 1`. В ней те же `totals`, что у JSON-экспорта сессии (`projecthub-swarm-session` v1), и сводка агентов
     (id, имя, движок, роль, модель, статус, usage, чекпоинты, откаты). Дальше идут события всех агентов с полем
     `agentId`. JSON-экспорт сессии не менялся по формату, но теперь включает `checkpoints`, `rewinds` и `trace` агента.
7. **Исправление учёта usage.** `recordUsage(..., 'add')` для Claude CLI вызывается один раз на `message.id`. Повторы
   того же сообщения бюджет больше не завышают. По той же причине лимит ходов роли (`maxTurns`) считает сообщения
   модели, а не события `assistant`: раньше ход с инструментом засчитывался дважды.

## Consequences

- Плюс: откат к любому ходу со снимком файлов, включая неотслеживаемые. Отмена отката — тот же механизм. В ветку
  победителя служебные снимки не попадают, squash не нужен.
- Плюс: таймлайн отвечает, что агент делал, сколько заняли модель и каждый инструмент, какие были решения HITL и
  переключения модели, сколько стоил ход. Трасса выгружается в JSONL для задачи или PR.
- Плюс: бюджет Claude CLI внутри хода больше не завышен повторами одного сообщения.
- Минус: снимок на каждый ход с инструментами — это `git add -A` по временному индексу. На больших деревьях с
  множеством неигнорируемых файлов это заметная работа. Одинаковые деревья не дублируются, а операции идут в очереди
  агента, вне потока событий.
- Минус: снимок хода отражает состояние в момент выполнения git, а не в момент события: он идёт в очереди, чтобы
  не тормозить разбор stream-json. Обычно между результатом инструмента и следующим инструментом есть время модели
  (в живом прогоне — 1,7 с), и снимок успевает раньше. Но при очень быстрых ходах он может захватить часть работы
  следующего хода. Тест с фейковым CLI без паузы это воспроизвёл.
- Минус: стоимость хода Claude CLI — оценка: частичный `output_tokens` в `assistant`. Точна только стоимость запуска
  из `result`.
- Минус: после отката staged-файлы снимка становятся неотслеживаемыми (индекс возвращается к родителю). Содержимое
  при этом совпадает со снимком.
- Долг: API-агенты Swarm не исполняют инструменты. Таймлайн покажет длительности, как только Swarm получит исполнитель
  (TASK-101: исполнитель с HITL для API-движка Swarm по [[decision-10]]). Codex и Gemini — только запуски, до TASK-71.
  Продолжение после отката в handoff и цикле «до готовности» — TASK-102.
- Проверено вживую 2026-09-19 настоящим Claude CLI 2.1.275 (`--model haiku`) через `AgentFleetService` во временном
  git-репозитории:
  - сценарий: Read `a.txt` → Write `b.txt` → Write `c.txt`, 4 хода;
  - длительности инструментов: 27, 33 и 31 мс;
  - чекпоинты появились только у ходов с Write (#2, #3); Read дерево не менял, снимок `end` совпал с #3 и не
    дублировался;
  - откат к #2 удалил `c.txt`, `git status` после него чистый, в ветке — `rewind(implementer): чекпоинт #2 (после
    хода 2)` поверх `base`;
  - продолжение шло новой сессией CLI (другой `session_id`) с пояснением об откате;
  - стоимость: $0.0325 + $0.0242 = $0.0567 (`provider`); трасса — 33 строки JSONL.
  Собранный exe на копии userData показал вкладку «Таймлайн» с этой сессией.
- Реализация: TASK-72 (подзадачи 72.1–72.5): `checkpointGit.ts`, `checkpointService.ts`, `agentTrace.ts`,
  `agentTraceTypes.ts`, `agentFleetService.ts`, `aiAgentService.ts` (`onToolBoundary`), `swarmSessionStore.ts`,
  `swarmExport.ts`, `AgentTimelinePanel.tsx`, `src/lib/agentTimelineView.ts`. Тесты: `checkpointGit.test.ts`,
  `agentTrace.test.ts` (фикстура `claude-cli-stream-2.1.275-tools.jsonl`), `agentCheckpointsFleet.test.ts`,
  `agentTimelineView.test.ts`, дополнение `swarmExport.test.ts`.
