## Context

До TASK-101 API-агент Swarm (`agentFleetService.runApiAgent`) вызывал `aiAgentService.streamChat` без
`executeTool`. Модель получала описания инструментов, но Swarm их не исполнял: вызов только писался в лог,
а в таймлайне оставался «не исполнен» ([[decision-45]] п. 3, долг). Многошаговый tool-loop с исполнением
был только в AI Studio (`claudeBridgeService.executeApiTool` и `handleApiToolCall`, TASK-82,
[[decision-27]] п. 10).

Что показала проверка кода и вживую (2026-09-19):

- **Исполнитель AI Studio привязан к чату.** В `handleApiToolCall` жёстко записан `origin: 'studio'`, в
  запросах HITL нет `agentId`, `agentName` и `role`. Права роли не применяются: allow-список
  `permissions.allowedTools` не проверяется, `allowFileRead: false` игнорируется. Политика там своя,
  ветвлениями, а не общая `evaluateToolRequest`, по которой Swarm уже решает за Claude CLI.
  `requestApproval` и `runCommandTool` ставят статус проекта AI Studio (`setProjectStatus(projectPath)`),
  карточки и статусы вызовов уходят в `onChunk` сессии чата, `spawn_subagent` регистрирует подагента
  AI Studio. Если передать туда worktree слота как `projectPath`, в статусах проектов появился бы
  «проект» с путём worktree.
- **Без исполнителя OpenAI-совместимые провайдеры инструментов вообще не получали.** `streamChat` отдаёт им
  `tools` только вместе с `executeTool`. API-слот на Ollama работал как чат.
- **Остановка API-агента не прерывала стрим.** `AbortController`, который `runApiAgent` регистрирует для
  остановки слота и бюджета, ни с чем не был связан: `streamChat` создаёт свой контроллер по `sessionId`.
  Если же стрим прерывали (`abortStream`), `streamChat` не вызывал ни `onComplete`, ни `onError`, и промис
  `runApiAgent` не завершался бы.
- **Usage API приходил одним итогом** в конце `streamChat`. Бюджет слота внутри многошагового хода не
  проверялся.
- **Флаг `toolActivity`** (запрет fallback модели после первого инструмента, [[decision-44]] п. 6)
  ставился по чанку `toolCall`, то есть по намерению модели, а не по исполнению. У Anthropic API вызов без
  исполнения ложно запрещал переключение модели. OpenAI-совместимым провайдерам инструменты не
  передавались, поэтому у них этого не было.
- **Tool calling моделей Ollama** (`/v1/chat/completions`, stream, `read_file` и `write_file`):
  `qwen2.5:7b-instruct` на Ollama 0.34 вызвала `read_file({"filePath":"input.txt"})` за 2,3 с, usage в
  стриме есть. `ornith:35b` на 192.168.1.11 (Ollama 0.31.2) сделала тот же вызов за 93 с вместе с загрузкой
  модели.

Рассмотренные и отвергнутые варианты:

1. **Вызвать `claudeBridgeService.executeApiTool` из Swarm, добавив в `req` метаданные агента.** Отвергнут.
   Пришлось бы протащить `origin`, агента и права роли через код, который разговаривает с чатом AI Studio
   (статусы проекта, карточки, подагенты). Политика осталась бы ветвлениями, отличными от политики
   Claude CLI в Swarm, так что у двух движков одного слота были бы разные правила.
2. **Сразу перевести AI Studio на новый исполнитель.** Отложено. Поведение AI Studio заметно меняется:
   чтение вне корня сейчас отклоняется, а по общей политике уходит в карточку. Меняются карточки с диффом в
   чате, подагенты и фоновые команды. Это отдельная задача со своей проверкой UI (TASK-103).
3. **Лимит шагов независимо от `maxTurns` роли.** Отвергнут. Ход API-движка — это запрос к модели
   ([[decision-45]] п. 3), так что `maxTurns` и есть лимит шагов tool-loop. Две настройки одного смысла
   расходились бы.
4. **Проверка бюджета только по итогу хода.** Отвергнута. Многошаговый ход с десятками запросов мог бы
   потратить весь бюджет до первой проверки.

## Decision

1. **Общий исполнитель, отдельный от чата AI Studio.**
   - Чистый модуль `apiToolPolicy.ts` без Electron решает, что делать с вызовом. Он нормализует имя и
     аргументы и сверяет инструмент с allow-списком роли: имя API-инструмента засчитывается и под
     именем-аналогом Claude Code (`read_file` ↔ `Read`, `write_file` ↔ `Write`/`Edit`, `run_command` ↔
     `Bash`, `ask_question` ↔ `AskUserQuestion`). Вердикт даёт та же `evaluateToolRequest`
     ([[decision-10]]), что решает за Claude CLI в Swarm. `list_dir` и `search_rag` проверяются как чтение.
   - Там же чистые функции выбора инструментов `computer_*`, лимита шагов и формы вопроса.
   - Сервис `apiToolExecutor.ts` исполняет вызов. Зависимости (очередь HITL, запись файла, команда,
     поиск по документации, прокси `computer_*`) внедряются, поэтому сервис покрыт unit-тестами без
     Electron и сети.
   - AI Studio пока остаётся на своём исполнителе. Перевод на общий — TASK-103.
2. **HITL и аудит.**
   - Запрос HITL несёт `sessionId: swarm-<agentId>`, `origin` (`swarm`, `handoff` или `assigned`), `engine: 'api'`,
     `agentId`, `agentName`, `role` и имя инструмента.
   - `projectPath` запроса — рабочий каталог слота, как у Claude CLI в Swarm (`prepareCliPermissions`
     получает тот же путь).
   - Правила — глобальные настройки auto-approve AI Studio, суженные правами слота (`applyRolePermissions`).
   - Корень файлов и команд — worktree слота. Запись вне него отклоняется без карточки (`outside-project`).
     Чтение вне него уходит в карточку (`read-outside`), как у Claude CLI.
   - В аудит пишется каждое решение, включая авто-решения с именем правила, а после исполнения — `outcome`
     по `requestId`.
   - `ask_question` в Swarm — карточка-вопрос в Центре решений, ответ возвращается модели.
   - Фоновые команды (`run_command` с `background: true`) в Swarm не запускаются: процесс пережил бы агента
     и попал бы в менеджер процессов основного дерева. Модель получает ошибку с советом запустить команду
     с ожиданием.
3. **Остановка.** Контроллер отмены API-слота вызывает `claudeBridgeService.abortSession(swarm-<agentId>)`.
   Это одновременно прерывает стрим, отменяет ожидающие карточки HITL агента и убивает его команды.
   Если `streamChat` вернулся без `onComplete` и `onError` (прерван), ход завершается сам, статус
   остановки или бюджета сохраняется. Перед каждым инструментом исполнитель проверяет, что агент ещё
   `running`.
4. **Лимиты.**
   - `maxSteps` tool-loop = `maxTurns` роли (1…100), без роли — `DEFAULT_MAX_TOOL_STEPS` (25). Ход API —
     запрос к модели, поэтому `maxTurns` значит одно и то же у Claude CLI (сообщения модели) и у API.
     `ENGINE_CAPABILITIES.api.maxTurns` становится `true`.
   - Когда лимит исчерпан, вызовы последнего шага не исполняются. Граница `step_limit` пишет в лог слота
     «Достигнут лимит ходов роли», ход завершается как у Claude CLI.
   - Счёт шагов идёт на запуск (итерацию цикла «до готовности»), как у Claude CLI.
5. **Бюджет по шагам.** Новая граница `step_usage` отдаёт usage каждого запроса к модели, сразу после
   ответа и до исполнения инструментов. Если сервер usage не прислал, берётся оценка с `estimated`,
   [[decision-42]]. Swarm пишет его через `recordUsage(..., 'add')`, так что `enforceBudget` останавливает
   слот между шагами. Итог `streamChat` по-прежнему заменяет сумму (`replace` с базой прежних запусков,
   [[decision-28]] п. 6). В трассу идёт `usage` со `scope: 'turn'` на каждый ход.
6. **`computer_*`.** По умолчанию инструменты управления компьютером API-слоту не передаются. Передаются
   только при трёх условиях: цикл «до готовности», задача с label `computer-use`, управление компьютером
   включено в ProjectHub (правило 20 infra-dev, [[decision-27]] п. 6). В этом случае вызовы идут через
   `computerUseService.callTool` с `origin` слота, `doneLoop`, `taskAllowsComputerUse` и `autoApprove` роли,
   и прокси повторно применяет свою политику. `tools` роли фильтрует и их: у роли с явным списком категорий
   `computer_*` нет.
7. **Fallback модели.** `toolActivity` ставит исполнитель в момент исполнения инструмента, после политики
   и одобрения, а не чанк `toolCall`. Вызов, отклонённый политикой или человеком, переключение модели не
   запрещает. Исполненный — запрещает ([[decision-44]] п. 6).
8. **Трасса и чекпоинты.**
   - `run_start` API-агента больше не несёт `toolsExecuted: false`. Длительности и статусы берутся из
     `onToolBoundary`. Длительность включает ожидание решения человека.
   - `onToolBoundary` может вернуть промис, и tool-loop ждёт его после результата инструмента. Swarm
     возвращает промис снимка `turn`, когда исполнены все вызовы шага. Так чекпоинт хода API снимается до
     следующего запроса к модели, без гонки, описанной в [[decision-45]] (Consequences).
   - AI Studio и голос `onToolBoundary` не передают, их поведение не меняется.
   - Событие `hitl` трассы несёт `toolId` вызова, который исполняет API-агент. Таймлайн привязывает решение
     сначала по нему, а эвристику «последний вызов этого инструмента» оставляет для Claude CLI и старых
     трасс. Без этого два `write_file` одного шага получали оба решения на второй вызов. Так вышло в живом
     прогоне qwen2.5.

## Consequences

- Плюс: API-слот Swarm работает как агент на любом провайдере, включая локальные модели Ollama. Правила
  HITL у него те же, что у Claude CLI в том же слоте.
- Плюс: бюджет API-агента срабатывает внутри хода, а остановка слота реально прерывает стрим и команды.
- Плюс: у API-агента в таймлайне есть длительности, статусы, usage и чекпоинты ходов.
- Минус: в AI Studio и Swarm два исполнителя API-инструментов с разной политикой, пока не сделана TASK-103.
- Минус: длительность инструмента с карточкой HITL включает время реакции человека. Отдельно время решения
  видно по событию `hitl` в трассе.
- Минус: фоновых команд в Swarm нет. Dev-сервер для проверки агент запустить не сможет.
- Проверено вживую 2026-09-19 настоящим `AgentFleetService`. Проект — временный git-репозиторий в
  scratchpad, у слота свой worktree. Auto-approve выключен. Запись одобрялась внешним MCP-клиентом
  (`projecthub_list_pending_approvals` → `projecthub_approve_action`) через встроенный MCP-сервер:
  - `qwen2.5:7b-instruct` (localhost): ход 1 — `read_file` (авто, 4 мс); ход 2 — `write_file` с верным
    `HELLO FROM SWARM API AGENT` (карточка, `decidedBy: mcp`, 499 мс вместе с ожиданием); чекпоинт после хода
    2; всего 5 с. В другом прогоне модель сделала все три вызова одним шагом, до результата чтения, и
    записала в файл строку `$(cat input.txt | tr …)`. Это качество модели, а не harness.
  - `ornith:35b` (192.168.1.11): 3 хода, 93 с, из них 89 с — первый запрос с загрузкой модели. Файл верный,
    usage по ходам 1257/70, 1306/144 и 1414/26 токенов.
  - В аудите у каждого решения и `outcome` есть `origin: swarm`, `agentId`, `role: implementer` и `filePath`.
  - Адрес прежнего провайдера `ollama` API-слот берёт из настроек AI Studio, а не из `baseUrl` слота
    ([[decision-40]]). Удалённую Ollama задают профилем.
  - Собранный exe на копии userData показал таймлайн сессии ornith. У инструментов длительности, «успех» и
    решения («разрешено (auto)», «запрос → разрешено (mcp)»), у ходов — токены, есть чекпоинт «после хода 2».
- Реализация: TASK-101 (подзадачи 101.1–101.3): `apiToolPolicy.ts`, `apiToolExecutor.ts`,
  `apiToolExecutorDeps.ts`, `agentFleetService.runApiAgent`, `aiAgentService` (границы `step_usage` и
  `step_limit`, ожидание промиса `onToolBoundary`), `agentTrace.ts` (`toolId` у `hitl`), `roleEngineAdapter.ts`
  (`api.maxTurns`). Тесты: `apiToolPolicy.test.ts`, `apiToolExecutor.test.ts`, `apiAgentToolsFleet.test.ts`.
