## Context

Контекст агента ProjectHub собирается заново на каждый запуск (`contextBuilder.buildAgentContext`,
[[decision-18]]): задача и критерии, чанки RAG, GitNexus, git-статус. Всё, что агент узнал о
проекте сам — что пробовали, почему отказались, где грабли окружения, — пропадает между сессиями,
движками и ветками. Конкуренты закрывают это памятью (context notes у Astra, авто-память Claude
Code, persistent memory у Hermes — doc-10). TASK-76 добавляет память проекта, одинаковую для всех
движков.

### Что выяснено при разборе (2026-09-26)

- **Backlog.md не трогает чужой каталог внутри `backlog/`.** На временном проекте с
  `backlog/memory/mem-1 … .md` и `MEMORY.md`: `backlog doc list`, `task list` и `search` их не
  видят; веб-интерфейс (`backlog browser`) — тоже: `/api/docs`, `/api/tasks`, `/api/decisions`,
  `/api/search` возвращают только свои сущности, ошибок нет. ProjectHub тоже слеп к каталогу:
  `docsService` сканирует только `docs/` и `decisions/`, `backlogWatcher` следит только за
  `tasks/`, сканер RAG приложения (`ragSearch.scanProjectMarkdownFiles`) — `docs/`, `decisions/`,
  `tasks/`. Значит каталог безопасен, но показывать и искать память должен сам ProjectHub.
- **Индекс docs-rag двухслойный.** Скрипты инфраструктуры (`scripts/rag/docs-hash.mjs` →
  `DOC_ROOTS`, `index-docs`, `check-index`, `validate-docs.mjs`) обслуживают MCP `docs-rag` агента-
  оболочки; приложение ищет своим `ragSearch` (векторный индекс проекта, если есть, иначе поиск по
  словам). Каталог памяти нужно добавить в оба слоя.
- **Движки получают инструменты по-разному.** Claude CLI (AI Studio, Swarm, Handoff, цикл «до
  готовности», узлы плана) подключается к встроенному MCP-серверу с `phSession`, по которому
  `claudeBridgeService` знает сессию и её `projectPath`; у агентов Swarm это путь **worktree**
  (`<проект>/.worktrees/<slug>`), а не корень проекта. API-агент (AI Studio и Swarm) вызывает
  инструменты через общий исполнитель в процессе ([[decision-46]], [[decision-47]]). Codex и
  Gemini CLI к MCP-серверу ProjectHub сейчас не подключены (TASK-85, TASK-77).
- **Готового детектора секретов нет.** Есть два маскировщика — `hitlAudit.redactSecrets`
  (Bearer, `key=value`, `sk-`, `gh*_`, `xox*-`, `AKIA`, пароли в URL, `FOO_TOKEN=`) и
  `providerErrors.redactSecrets` (префиксы ключей провайдеров). Они заменяют, а не отвергают, и
  шаблон `key=value` для отказа слишком широк: фраза «password: хранится в safeStorage»
  ложно сработала бы.
- **Implementation Notes задач сейчас никто не пишет.** Цикл «до готовности» пишет только
  `## Final Summary` и только при успехе ([[decision-28]] п. 7); неудачные попытки не оставляют
  следа в задаче.
- **Бюджет контекста общий.** `assembleContext` режет части в порядке `task > rag > gitnexus > git`
  при `maxChars` 6000; без `taskId` результат пустой.

### Рассмотренные альтернативы

- **`.projecthub/memory/` в корне проекта.** Отдельно от Backlog, но это второй источник знаний
  рядом с `backlog/` вопреки [[decision-3]], и такой каталог легко попадает под `.gitignore`
  вместе с runtime-состоянием; другой компьютер после `git pull` памяти бы не получил.
- **`<userData>`** (как у самого Claude Code). Память не едет с проектом и не видна другим людям и
  машинам — противоречит [[decision-7]] п. 3.
- **Память как документы `backlog/docs/doc-N`.** Backlog.md и его веб-интерфейс сразу показывали
  бы факты, но смешали бы короткие рабочие заметки агента с документацией, а номера `doc-N` и
  правило 13 рассчитаны на человеческие документы.
- **Писать память в worktree агента.** Факт уезжает вместе с веткой и теряется, если ветку
  отбросили, — а знание «почему этот путь не сработал» ценнее всего именно тогда. Параллельные
  агенты его тоже не видят до слияния.
- **Семантическая дедупликация через эмбеддинги.** Точнее, но медленная, недетерминированная и
  зависит от наличия модели и индекса. Для коротких фактов хватает сравнения по словам.
- **Заметку хода пишет сам агент через MCP.** Не работает для Codex/Gemini без MCP и ненадёжно
  для малых моделей, которые пропускают вызовы инструментов.
- **Подтверждение каждой записи в памяти через HITL.** Шумно: память пишется часто и не меняет код.
  Запись и так ограничена одним каталогом, форматом и фильтром секретов.

## Decision

1. **Место — `backlog/memory/` проекта, в git.** Один факт — один файл
   `backlog/memory/mem-<N> - <Title-Slug>.md` (slug до 60 символов — ENAMETOOLONG на Windows),
   индекс — `backlog/memory/MEMORY.md`. Каталог не является сущностью Backlog.md; ProjectHub сам
   его читает, показывает и индексирует.

2. **Формат факта** (чистый модуль `memoryFormat.ts`, unit-тесты):
   ```yaml
   ---
   id: "mem-12"
   title: "Короткий заголовок факта"
   description: "Одна строка: о чём факт и когда он нужен"
   type: "project"            # project | feedback | reference
   created: "2026-09-26 13:40"
   updated: "2026-09-27 09:10" # необязательно
   source: "task-76"          # task-N | session | user
   author: "claude-cli/architect" # необязательно: движок/роль
   ---
   Тело: сам факт и, для project/feedback, строки «Почему:» и «Как применять:».
   ```
   Все значения frontmatter — строки в кавычках (правило 16). Лимиты: заголовок до 100 символов,
   описание до 200, тело до 2000. `MEMORY.md` генерируется сервисом при каждой записи и удалении —
   одна строка на факт `- [title](file) — description`, по возрастанию номера; руками его не правят.

3. **Запись всегда идёт в основное дерево зарегистрированного проекта.** Путь сессии (worktree
   агента) приводится к корню проекта через реестр проектов: корень — зарегистрированный проект,
   внутри которого лежит путь. Путь вне зарегистрированных проектов — отказ. Коммит памяти делает
   человек, как и правки задач из GUI; автокоммита нет. Так же уже устроены отметки критериев цикла
   «до готовности» ([[decision-28]] п. 3).

4. **Инструменты `memory_write`, `memory_search`, `memory_delete` — одна реализация
   (`memoryService`) для всех поверхностей:**
   - Claude CLI — встроенный MCP-сервер (`mcp__projecthub-hitl__memory_*`); проект берётся из
     контекста сессии `phSession`, у внешнего MCP-клиента — из явного `projectPath` (проверяется по
     реестру) или активного проекта. Как и `computer_*`, эти инструменты не идут через второй
     запрос `permission_prompt`: политику применяет сам сервис.
   - API-агент — общий исполнитель инструментов ([[decision-46]]), отдельный вид инструмента
     `memory` в `apiToolPolicy`, без карточки HITL.
   - Codex и Gemini CLI — пока только чтение через контекст (п. 6) и заметки хода (п. 8); запись
     появится вместе с подключением этих движков к MCP-серверу ProjectHub (TASK-85, TASK-77).
   - `memory_write({ title, description, body, type, source?, replace? })` возвращает id факта;
     `replace: "mem-N"` обновляет существующий факт. `memory_search({ query, limit? })` ищет по
     словам в заголовке, описании и теле (свежие факты находятся сразу, без переиндексации).
   - Каждая запись и удаление фиксируются в аудит-логе HITL как автоматическое решение с правилом
     `memory` (путь и id, без содержимого — [[decision-10]] п. 4).

5. **Гигиена записи — чистые функции с тестами, отказ вместо тихой правки:**
   - **Секреты.** Общий модуль шаблонов `secretPatterns.ts` с детектором `detectSecrets(text)`:
     известные префиксы ключей (`sk-`, `sk-ant-`, `sk-or-`, `gsk_`, `xai-`, `gh*_`, `xox*-`,
     `AKIA`), блоки `-----BEGIN … PRIVATE KEY-----`, JWT, пароли в URL, `Bearer <токен>` и
     `ИМЯ_СЕКРЕТА=значение` — только если значение похоже на секрет (от 12 символов без пробелов,
     буквы вместе с цифрами). Найден секрет — запись отклоняется с указанием вида находки, но без
     самого значения. `hitlAudit` переходит на те же шаблоны без изменения поведения.
   - **Дубликаты.** Перед записью факт сравнивается с существующими по словам (нормализация,
     коэффициент Жаккара по заголовку и описанию); выше порога запись отклоняется с id похожего
     факта — агент либо обновляет его через `replace`, либо уточняет формулировку.

6. **Чтение через `contextBuilder`:** новая часть контекста `memory` с приоритетом сразу после
   задачи (`task > memory > rag > gitnexus > git`). В неё входят строки `MEMORY.md` и тела до трёх
   фактов, найденных поиском по заголовку и описанию задачи; своя доля бюджета — до 1500 символов,
   чтобы память не вытесняла RAG. Часть собирается и без задачи — память проекта нужна и в
   свободной сессии AI Studio. Переключатель части — в `ContextAppliedCard`, как у остальных.
   Если у агента есть инструмент записи, в ту же часть добавляется короткая инструкция: сохранять
   через `memory_write` неочевидные выводы, которые пригодятся в следующих сессиях, и не сохранять
   то, что уже есть в коде, задачах и ADR.

7. **Индексация и проверки.** `backlog/memory` добавляется в `DOC_ROOTS` скриптов docs-rag
   (`index-docs`, `check-index`) и в сканер `ragSearch` приложения (категория `memory`).
   `validate-docs` проверяет файлы памяти: имя, frontmatter (строки, `type` из списка, `id`
   совпадает с именем файла), лимиты, отсутствие секретов и соответствие `MEMORY.md` набору
   файлов. Правило 13 infra-dev дополняется форматом памяти.

8. **Заметку хода пишет harness, не агент.** По завершении сессии агента, привязанной к задаче
   (слот Swarm/Handoff, цикл «до готовности», узел плана, назначенная задача), ProjectHub
   дописывает в `## Implementation Notes` задачи основного дерева (нативные маркеры
   `SECTION:NOTES`) одну короткую запись: дата, движок и роль, исход (успех, провал с причиной,
   остановка), число итераций, стоимость, ветка и последний коммит, и до 600 символов итогового
   сообщения агента (для цикла «до готовности» — поле `summary` его отчёта). Одна запись на сессию,
   а не на итерацию — цикл «до готовности» не задваивается с `Final Summary`, который он пишет при
   успехе; при неудаче заметка хода — единственный след попытки. Сессии AI Studio без задачи заметок
   не пишут.

## Consequences

**Плюсы.** Знание о проекте переживает сессии, движки и отброшенные ветки и едет с проектом через
git. Одна реализация на все поверхности, а заметки хода работают даже у движков без MCP. Каталог не
мешает Backlog.md и его веб-интерфейсу (проверено). Секреты и дубликаты отсекаются до записи,
каждая запись видна в аудите.

**Минусы и долг.**

- Codex и Gemini CLI до TASK-85/TASK-77 память только читают.
- Запись в основное дерево создаёт незакоммиченные изменения у человека, пока агент работает в
  worktree; параллельные записи двух агентов сериализуются в сервисе, но конфликт с ручной правкой
  того же файла возможен.
- Дедупликация по словам пропустит перефразированный дубликат; чистка остаётся за человеком (UI
  просмотра и удаления).
- Детектор секретов эвристический: экзотический формат токена пройдёт, а длинный буквенно-
  цифровой идентификатор после `TOKEN=` может дать ложный отказ.
- Backlog.md и его веб-интерфейс память не показывают — только ProjectHub.
- Изменение `DOC_ROOTS` меняет хэш документации: индекс docs-rag нужно пересобрать один раз.

### Проверено вживую (2026-09-26, TASK-76.6)

- **API-агент Swarm, `ornith:35b` (удалённая Ollama).** По задаче TASK-1 агент в своём worktree вызвал
  `memory_write`: факт `mem-1` появился в `backlog/memory` основного дерева (в worktree каталога нет),
  `source: task-1`, `author: api/<слот>`, тело — со строками «Почему:» и «Как применять:» из инструкции.
  Новая сессия без задачи ответила `make dist` из памяти в контексте. В задаче — заметка хода.
- **Две линии защиты от секретов.** Ключ `sk-ant-…` модель отказалась сохранять сама — сработала
  инструкция из части памяти. JWT, поданный как «идентификатор сессии из лога», модель попыталась
  сохранить; сервис отклонил запись (`deny: memory_write: secret_detected` в аудите), модель
  переформулировала факт без токена и сохранила `mem-2`.
- **`qwen2.5:7b-instruct` нестабилен в вызове инструментов:** в одном прогоне вызвал `memory_write`
  правильно, в другом напечатал вызов JSON-текстом. Это свойство модели, а не контура.
- **Claude CLI** в этот день не проверен вживую: DNS машины не резолвил `api.anthropic.com` (`ENOTFOUND`
  у CLI, таймауты `nslookup`). Путь Claude CLI через встроенный MCP закрыт сквозным тестом с настоящим
  MCP-сервером и SSE-клиентом (`mcpMemoryTools.test.ts`).
- **Найдено и исправлено живым прогоном:** API-слот Swarm передавал в `streamChat` путь worktree как
  `projectPath`, и контекст искал память в worktree, где её нет. Теперь `projectPath` — корень проекта,
  `workspaceRoot` — worktree, как в AI Studio. Сессия арены получает `completed`, даже если её агент упал, —
  заметка хода выводит исход из статусов агентов («провал», причина — ошибка агента). Запись заметки
  атомарная: `writeFile` обнулял файл задачи, и параллельное чтение видело пустую задачу.

Пересматривает [[decision-28]] п. 7: при неудаче цикла файл задачи теперь получает заметку хода
(критерии и статус по-прежнему не трогаются).
