## Context

До TASK-74 ProjectHub запускал агента без нажатия человека в одном месте: автозапуск задачи,
назначенной на этот хост (TASK-66, [[decision-19]] п. 5). `backlogWatcher` на каждое изменение
файла задачи открытого проекта вызывал `assignedTaskRunner.handleTaskFile`, условия — в чистом
`assignedTaskRules.decideAutoStart` (явный `@hostId`, статус `To Do`/`In Progress`, нет активного
роя, пауза 10 минут). Включение — флаг `autoStartAssignedTasks` в `remote-control.json`.
Claude Code (Routines), Codex Cloud и Cursor запускают фоновых агентов по расписанию и событиям;
doc-10 фиксирует это как пробел. Задача обобщает автозапуск в правила «триггер + условие +
действие» с журналом и лимитами.

Что показал разбор кода:

1. **Шина** ([[decision-13]]) публикует `agent:started|finished|failed|modelFallback`,
   `hitl:*`, `swarm:finished`, `process:crashed`, `pr:created`, `pr:checksFailed`,
   `remote:deviceConnected`, `federation:peerEvent`. Событий задач нет вовсе: `backlogWatcher`
   шлёт в рендерер «файл изменился» без разбора, что именно изменилось. `docs.changed` и
   `device.connected` в смысле «ПК федерации подключился» тоже нет. `pr:checksFailed`
   публикуется на каждом опросе списка PR, пока проверки красные, и только пока открыта вкладка
   PR, — дубликаты снимает дедупликация уведомлений, а не издатель.
2. **Ограничения [[decision-26]] п. 7 в коде обеспечены не полностью.** Для слота с включённым
   auto-approve Gemini CLI запускается с `--approval-mode yolo`, а Claude CLI при недоступном
   встроенном MCP-сервере падает в залогированный `--dangerously-skip-permissions`. Для запуска
   человеком это осознанный fallback ([[decision-10]] п. 1), для автономного — нет. Codex уже
   всегда идёт с `--sandbox workspace-write` (или `read-only`). Политика управления компьютером
   (`computerPolicy`) уже запрещает `computer_*` для `origin: automation | assigned` (правило 20).
3. **Встроенный MCP-сервер виден агентам.** Claude CLI агента подключается к нему с
   `phSession`; инструмент `automation_run`, доступный агенту, дал бы агенту запускать агентов в
   обход лимитов цепочки.
4. **`.projecthub.json` приходит через git.** Проектное правило, которое само становится
   активным после `git clone`/`git pull`, — это автозапуск чужого кода и трата чужого бюджета.
   Агент в worktree тоже может изменить `.projecthub.json`, и после слияния правило поменяется.

Рассмотрены и отвергнуты:

- **cron-библиотека** (`croner`, `cron-parser`). По правилу 17 runtime-зависимость становится
  external и едет в `app.asar`; ради разбора пяти полей и поиска следующей минуты это лишний
  размер и ещё одна зависимость под `check-bundle`. Нужен ровно стандартный 5-полевой cron —
  своя чистая реализация короче и тестируется целиком.
- **Часовой пояс на правило (IANA).** Требует расчёта через `Intl` с переходами DST в чужой зоне;
  ProjectHub — десктоп одного человека, локального времени машины достаточно.
- **Долгий `setTimeout` до следующего срабатывания.** Таймер «уплывает» при сне ноутбука и не
  переживает смену системного времени; вместо него — тик раз в 30 секунд со сверкой с
  `nextRunAt`.
- **Догонять все пропущенные срабатывания** при старте приложения. Ноутбук, закрытый на ночь,
  утром запустил бы пачку агентов разом. По умолчанию пропущенное пропускается.
- **Доверять проектным правилам по факту регистрации проекта** или «раз и навсегда» для
  проекта. Первое — автозапуск при клоне; второе — правило, поменявшееся после `git pull`
  (в том числе руками агента), запустилось бы без взгляда человека.
- **Защита от циклов только cooldown'ом.** Cooldown ограничивает частоту, но не цепочку
  «роль → `swarm:finished` → другая роль → …»; нужен и учёт причинности.
- **Отдельный механизм для назначенных задач рядом с Automations.** Два места, где приложение
  само запускает агента, с разными лимитами и журналами — ровно то, что задача убирает.

## Decision

1. **Модель правила** — чистый модуль `automationRules.ts` (zod-схема, unit-тесты):
   `{ id, name, enabled, trigger, conditions, action, limits }`.
   - **Триггеры:** `cron` (5 полей), `manual` и события шины, которые реально публикуются:
     `task.assigned`, `task.statusChanged`, `swarm.finished`, `agent.failed`,
     `process.crashed`, `pr.created`, `pr.checksFailed`, `device.connected`
     (`remote:deviceConnected`). В UI и схеме нет триггеров, которых шина не знает:
     `docs.changed` отложен до появления события (см. Consequences).
   - **Условия:** проект (глобальное правило — список проектов или все; проектное — всегда свой
     проект), labels (любой из), статус «в» и «из» для `task.statusChanged`, исполнитель по
     шаблону, исход для `swarm.finished` (`completed | failed | stopped`), имя процесса для
     `process.crashed`, «нет активного роя по задаче» (всегда для действий с агентом).
   - **Действия:** `runAgent` (роль, одиночный слот или цикл «до готовности», промпт-шаблон с
     `{{taskId}}`, `{{taskTitle}}`, `{{event}}`; всегда в worktree), `runChecks` (проверки проекта
     по `checkIds` или все, в основном дереве), `reindexDocs` (скрипт `index-docs` проекта),
     `notify` (событие шины `automation:notify` → каналы `notificationService`), `projectAction`
     (действие `.projecthub.json`: `run`/`test`/`deploy`/`customActions[id]`, разово через
     `processManager.runOnce` с тайм-аутом).
2. **События задач в шине.** Одно новое событие `task:updated` (`taskId`, `title`, `status`,
   `assignee`, `labels`, `created`, `changes.status {from,to}`, `changes.assignee {from,to}`).
   Источник — `taskEventSource`: снимок frontmatter задач на старте наблюдения и чистый
   `diffTaskSnapshot`. Наблюдаются открытый проект (о смене сообщает `backlogWatcher`) и проекты,
   явно названные во включённых правилах с триггерами задач. `task.assigned` и
   `task.statusChanged` — фильтры поверх `task:updated`; само `task:updated` пользовательским
   триггером не показывается (им пользуется встроенное правило, п. 7). В уведомления события
   задач не идут.
3. **Хранение.**
   - Глобальные правила и настройки — `<userData>/automations.json`; изменяемое состояние
     (`lastRunAt`, `nextRunAt`, счётчики дня, пауза) — отдельно в `<userData>/automations-state.json`,
     чтобы конфиг оставался человекочитаемым ([[decision-7]]).
   - Проектные правила — секция `automations` в `.projecthub.json`, едут через git.
   - **Проектное правило активно только после явного включения человеком на этой машине.**
     Факт включения — `trust[<корень проекта>][<id правила>] = sha256(канонический JSON правила)`
     в `<userData>/automations.json`, не в проекте. Правило, чьё содержимое изменилось (git pull,
     правка агентом), получает статус «изменено — нужно подтверждение» и не срабатывает, пока
     человек не подтвердит новую версию. Новое правило в проекте по умолчанию выключено.
   - Журнал — `<userData>/automations-log.jsonl` с ротацией (2 МБ × 3 файла): запуск, итог,
     пропуски по лимитам, ссылка на `swarmId`, стоимость, длительность. Пропуски «условие не
     совпало» и «cooldown» не журналируются — иначе опрос PR заполнит журнал шумом.
4. **cron** — своя чистая реализация (`cronExpr.ts`): стандартные 5 полей
   (минута, час, день месяца, месяц, день недели), `*`, списки, диапазоны, шаги, имена месяцев
   и дней, `0` и `7` — воскресенье; если заданы и день месяца, и день недели — срабатывает по
   любому из них (как в Vixie cron). Без секунд, `L`, `W`, `#` и `@reboot`; макросы `@hourly`,
   `@daily`, `@weekly`, `@monthly` раскрываются. Время — локальное время машины. Переход на
   летнее время: несуществующие минуты пропускаются; повтор часа при переходе на зимнее время
   не даёт второго срабатывания (сверка по локальной метке «дата-час-минута» последнего запуска).
   Планировщик тикает раз в 30 секунд; срабатывание, опоздавшее больше чем на 5 минут
   (сон, закрытое приложение), считается пропущенным и обрабатывается по `catchUp` правила:
   `skip` (по умолчанию) или `once` — один запуск при первом тике, не пачка.
5. **Защита от циклов.**
   - **Причинность.** Каждый запуск получает `runId` и глубину цепочки. Сессия флота, запущенная
     правилом, помечается `automation: { ruleId, runId, depth }`. Событие, порождённое
     запуском (`swarm:finished`/`agent:*` той сессии; `task:updated` по задаче активного запуска
     или завершённого не более 2 минут назад), наследует его цепочку: правило не реагирует на
     события своего же запуска, остальные получают глубину `depth + 1`, выше 3 запуск
     отклоняется с записью в журнал.
   - **Cooldown** на пару «правило + предмет события» (задача, PR, процесс; для cron — само
     правило): по умолчанию 10 минут, не меньше 1 минуты для действий с агентом.
   - События `automation:*` триггерами быть не могут.
6. **Лимиты и границы автономности** ([[decision-26]] п. 7, [[decision-10]]).
   - `maxRunsPerDay` на правило (по умолчанию 20) и **обязательный** `dailyBudgetUsd` для
     `runAgent`. Бюджет запуска = min(бюджет в правиле, остаток дневного); он становится бюджетом
     сессии, и `enforceBudget` останавливает агента на лету. Стоимость запусков копится по
     `totalCostUsd` сессии; неизвестная стоимость (локальная модель без цен) считается нулём, и
     тогда ограничителем остаётся число запусков.
   - Исчерпан дневной бюджет или число запусков — правило приостанавливается до локальной
     полуночи (`pausedUntil`, причина в состоянии), в шину уходит `automation:suspended`, и
     уведомление идёт по новому виду `automation` матрицы каналов (по умолчанию трей, ОС,
     Telegram, Remote). Человек может снять паузу вручную.
   - Одновременно работает не больше 2 агентов, запущенных автоматизациями (настройка);
     сверх — пропуск с записью в журнал, а не очередь.
   - **Автономный запуск** (`origin: automation` или `assigned`) всегда проходит через HITL-контур
     ProjectHub с политикой роли. Запрещены: fallback Claude CLI на
     `--dangerously-skip-permissions` (при недоступном MCP-сервере агент не стартует),
     `--approval-mode yolo` Gemini CLI (в автономном режиме — `default`), sandbox шире
     `workspace-write` у Codex. Авто-одобрение по правилам (списки, запрет записи вне корня)
     допустимо — это и есть HITL-политика роли. Управление компьютером запрещено (правило 20).
   - **Запросы одобрения без человека** ждут тайм-аута роли (`approvalTimeoutMin`), уходят во все
     каналы уведомлений и по истечении получают deny ([[decision-10]] п. 2); итог запуска в журнале.
   - `projectAction` с `requiresConfirmation: true` (например, deploy) автоматизация не
     выполняет: подтвердить некому. Статус `Done` автоматизации не выставляют (правило 5).
   - Автоматизации читают память проекта так же, как любой агент ([[decision-51]]): часть
     `memory` контекста и инструменты `memory_*`.
7. **Автозапуск назначенных задач — встроенное правило `builtin:assigned-tasks`.**
   Триггер `task:updated` (любое добавление или изменение файла задачи — как раньше), условие —
   неизменённый `decideAutoStart`, действие — `runAgent` роли из `assignee`. Включение
   по-прежнему хранится флагом `autoStartAssignedTasks` в `remote-control.json` (переключатель в
   Remote Control и в Automations пишут одно и то же поле). Добавляются общие лимиты правила:
   дневной бюджет (по умолчанию 5 USD, настраивается), число запусков, журнал, причинность.
   Прямой вызов `assignedTaskRunner` из `backlogWatcher` удаляется.
8. **Внешнее управление.** Во встроенном MCP-сервере — `automation_list` (правила, состояние,
   последние запуски) и `automation_run` (ручной запуск по `ruleId`). `automation_run` работает
   только для внешних клиентов (Remote Control, Telegram, Claude Code в терминале); из сессии
   агента ProjectHub (`phSession`) он отклоняется. Ручной запуск проходит те же доверие, лимиты и
   журнал, что и событийный, но без cooldown. IPC — те же операции плюс сохранение глобальных
   правил, подтверждение проектных и чтение журнала.

## Уточнения по факту реализации (TASK-74)

1. **Модули.** Чистые: `cronExpr.ts` (разбор и `planCronTick`), `automationRules.ts` (схема, события,
   матчинг, `gateRun`, учёт старта и стоимости, `attributeEvent`, `ruleHash`), `taskSnapshot.ts`
   (`diffTaskSnapshot`). Оркестратор `automationEngine.ts` получает все сервисы зависимостями и
   проверяется тестами без Electron; `automationService.ts` связывает его с флотом, проверками,
   процессами, реестром и шиной; `automationStore.ts` — файлы в userData; `automationActions.ts` —
   пять действий; `taskEventSource.ts` — наблюдение за задачами; `automationTools.ts` — MCP.
2. **Автономность определяется меткой `session.automation`, а не `origin`.** Ручной запуск назначенной
   задачи из карточки (`swarm:runAssigned`) остаётся запуском человека с прежним поведением;
   встроенное правило запускает с `origin: assigned` (прежняя подпись в HITL) и меткой
   `automation`, пользовательские правила — с `origin: automation`. Запреты п. 6 (нет fallback на
   `--dangerously-skip-permissions`, нет `yolo` у Gemini) действуют по метке.
3. **Общий путь запуска роли** — `agentFleetService.startRoleAgent` (одиночный слот или цикл «до
   готовности», бюджет запуска становится бюджетом сессии); `startAssignedAgent` стал обёрткой над ним
   с прежней сигнатурой.
4. **Проектное правило без поля `enabled` считается объявленным включённым** — срабатывает оно всё
   равно только после подтверждения; `enabled: false` в файле выключает правило на всех машинах.
   Подтверждение передаёт хэш показанной человеку версии: если файл успел измениться, IPC отказывает.
5. **Ручной запуск и «запустить сейчас»** не ждут выполнения действия: IPC возвращает `runId`, итог —
   в журнале и событии `automation:runFinished`. У правила на паузе кнопка скрыта, ручной запуск
   через MCP получает отказ `paused`.
6. **Уведомления.** Вид `automation` матрицы каналов: пауза по лимиту (`automation:suspended`) и
   сбой запуска (`automation:runFinished` с `failed`, клик ведёт в сессию роя); успешные запуски не
   уведомляют — их видно в журнале. Действие `notify` — событие `automation:notify`.
7. **Живая проверка (TASK-74.6):** проектные правила во временном репозитории не срабатывали до
   подтверждения; `task.statusChanged → Review` запустил проверки; cron `* * * * *` запустил роль на
   Claude CLI (haiku) через HITL ProjectHub с бюджетом запуска $0.01, `enforceBudget` остановил агента
   на $0.015, правило встало на паузу до полуночи с уведомлением, следующая минута агента не запустила.

## Consequences

- Плюс: одно место, где приложение само запускает агента, с одними лимитами, журналом и
  проверками; п. 7 [[decision-26]] наконец обеспечен и для назначенных задач.
- Плюс: клон или `git pull` не превращается в автозапуск: проектное правило работает только в
  той версии, которую человек видел на этой машине.
- Плюс: cron без зависимости; расчёт следующего срабатывания и DST проверены тестами.
- Минус: события задач есть только для открытого проекта и проектов, явно указанных в правилах;
  проект, который никто не наблюдает, событий не порождает. Встроенное правило, как и раньше,
  видит только открытый проект.
- Минус: пропущенные срабатывания по умолчанию теряются — сознательный размен против пачки
  запусков после сна.
- Минус: Gemini CLI в автономном режиме фактически работает только на чтение, пока нет
  HITL-моста для Gemini (TASK-77).
- Минус: `pr.checksFailed` и `pr.created` срабатывают только при опросе PR ProjectHub, то есть
  пока открыт проект с вкладкой PR; событие не приходит от GitHub напрямую.
- Долг: `docs.changed` (вотчер `backlog/docs`, `backlog/decisions`) и подключение ПК федерации
  как триггеры — после появления событий в шине.
- Реализация: TASK-74. Опирается на [[decision-10]], [[decision-13]], [[decision-19]],
  [[decision-26]], [[decision-28]], [[decision-49]], [[decision-51]], [[decision-7]], модалки —
  по [[decision-17]].
