## Context

Claude Code `/ultrareview`, Cursor BugBot и Copilot ревьюят PR фоновыми агентами и проверяют
собственные находки, прежде чем их показать. В ProjectHub были кирпичи: LLM-ревьюер Arena
([[decision-12]] п. 3, `reviewerPrompt.ts`), интеграция PR через GitHub CLI (`prService`),
Automations ([[decision-52]]). Связки «PR появился → ревью → комментарий» не было (doc-10).

Что показал разбор кода и машины:

1. **События PR.** `pr:created` публикуется только для PR, созданного из ProjectHub;
   `pr:checksFailed` — на каждом опросе списка, пока открыта вкладка PR. Событий «чужой PR
   открыт» и «в PR пришёл новый коммит» нет вовсе.
2. **Провайдер.** `prService` работает только с GitHub через `gh`; GitLab распознаётся по remote,
   но ни список, ни дифф, ни комментарий для него не реализованы. На машине разработки `gh` и
   `glab` не установлены — любое решение обязано честно деградировать без CLI.
3. **Ревьюер Arena** ходит в модель через `aiAgentService.streamChat` в режиме чата с инструментами
   чтения — это путь только для API-провайдеров; Claude CLI им не воспользоваться. Флот
   (`agentFleetService`) запускает любой движок в worktree с HITL, бюджетом, транскриптом и
   стоимостью, а `baseBranch` принимает произвольную ссылку — worktree можно создать на голове PR.
4. **Роли** сужают права слота: `permissions.allowedTools` отклоняет всё вне списка без карточки
   HITL. Флот не запускает `worktreeInit` в своих worktree — ревьюерам не нужно ставить зависимости.
5. **HITL** (`hitlService.request`) ждёт решения с любого канала (окно, Telegram, телефон) и
   пишет аудит ([[decision-10]]). Codex `review/start` недоступен: Codex не оплачен (TASK-71).

Рассмотрены и отвергнуты:

- **Ревью через путь ревьюера Arena (`streamChat`).** Закрывает только API-движки; Claude CLI
  выпадает, а транскрипта, бюджета сессии и «открыть сессию» нет.
- **Вебхуки GitHub.** Нужен публичный адрес или релей с состоянием — против local-first
  ([[decision-7]]); десктопу достаточно опроса.
- **Публиковать комментарий без человека** (настройка «сразу»). Комментарий в чужом PR —
  внешнее действие от имени пользователя; автономный запуск не должен его делать молча.
- **Approve / request changes через `gh pr review`.** Автоматическое одобрение запрещено задачей;
  проще исключить сам путь, чем охранять флаг.
- **Один ревьюер без проверки.** Главная претензия к LLM-ревью — ложные находки; адверсариальная
  проверка отдельным проходом отбрасывает их дешевле, чем читает человек.
- **Встроенное правило «ревьюить все PR».** Ревью стоит денег и пишет в чужие PR — его включают
  осознанно: правило Automations создаётся человеком или подтверждается как проектное.

## Decision

1. **События PR из опроса.** `prWatcher` опрашивает `gh pr list --state open` только для проектов,
   которым это нужно (включённые правила с триггерами `pr.opened` / `pr.updated`; глобальные без
   списка проектов — открытый проект), раз в 3 минуты. Снимок «номер → head SHA, черновик» хранится
   в `<userData>/pr-watch.json`, поэтому PR, открытый при закрытом приложении, даёт событие при
   следующем запуске. Первый опрос проекта — только базовая линия, без событий. Чистый
   `diffPrSnapshot` выдаёт `pr:opened` (новый номер) и `pr:updated` (другой head SHA, в том числе
   после force-push). Нет `gh`, нет авторизации, нет сети — опрос проекта пропускается с
   экспоненциальной паузой до 30 минут и одной записью в лог на смену состояния.
2. **Триггеры и действие Automations.** Схема [[decision-52]] получает триггеры `pr.opened`,
   `pr.updated` и действие `reviewPr`: `{ reviewers: [role, …] (1–3), verifier?: role,
   budgetUsd?, publish: 'hitl' | 'manual', includeDrafts: false }`. Для `reviewPr`, как для
   `runAgent`, обязателен дневной бюджет правила; действие считается запуском агента в лимитах
   параллельности. Черновики по умолчанию пропускаются. Ручной запуск — вкладка «Ревью» у PR
   (человек у экрана выбирает ревьюеров, проверяющего, бюджет и режим публикации).
3. **Идемпотентность.** Результат ревью — запись `<userData>/pr-reviews/<хэш проекта>/<номер>-<sha>.json`.
   Ревью того же head SHA не повторяется (событие пропускается, ручной повтор — явной кнопкой);
   новый SHA — новое ревью, прежнее остаётся в истории как устаревшее.
4. **Ревьюеры работают на чтение во флоте.** Голова PR забирается `git fetch origin
   +refs/pull/<N>/head:refs/projecthub/pr/<N>`, сессия fan-out с меткой `review` стартует от этой
   ссылки: у каждого ревьюера свой worktree с кодом PR. Слот получает роль и суженные права:
   `allowedTools` — только чтение и поиск, запись и команды отклоняются без карточки. Движок любой
   (Claude CLI, API-агент; Gemini — по его ограничениям). Автосудья Arena и заметки хода для сессий
   ревью не запускаются. В промпт идут PR (заголовок, описание, ветки), связанная задача Backlog.md
   (по `task-N` в ветке или заголовке — описание и критерии приёмки) и дифф `gh pr diff` (до
   60 000 символов, дальше ревьюер читает файлы сам).
5. **Формат находок** — последним блоком ограда ```` ```projecthub-review ```` с JSON
   `{ summary, findings: [{ file, line, endLine?, severity, category?, title, description,
   suggestion?, evidence? }] }`; без ограды — последний JSON-объект с `findings`. Серьёзность
   `critical | major | minor | nit` с синонимами (`blocker`, `high`, `medium`, `low`, `info`). Разбор —
   чистый модуль с zod-схемой; неразобранный ответ ревьюера не роняет ревью, а помечается.
6. **Судья: дедупликация и адверсариальная проверка.** Чистый `dedupeFindings` склеивает находки
   разных ревьюеров об одном месте (тот же файл, пересекающиеся строки с допуском 3, близкий текст по
   Жаккару слов) и считает согласие. До 20 уникальных находок (по серьёзности и согласию) уходят
   одному проверяющему — отдельный слот на чтение в worktree PR с задачей опровергнуть каждую:
   ответ ```` ```projecthub-verify ```` `{ verdicts: [{ id, verdict: confirmed | refuted | uncertain,
   reason, evidence }] }`. В комментарий идут только `confirmed`; `refuted` и `uncertain` видны в
   карточке. Ошибка проверяющего — находки остаются «не проверены», публикация не предлагается.
7. **Бюджет ревью** делится: 70 % — сессии ревьюеров, 30 % — проверяющему; для правила он не
   больше остатка дневного бюджета. Стоимость — сумма сессий, видна в карточке и журнале.
8. **Публикация — только `gh pr comment --body-file`, только после человека.** Режим `hitl`
   (по умолчанию) ставит в очередь HITL запрос с текстом комментария; одобрение с любого канала
   публикует, отказ или тайм-аут (24 часа) — нет. Режим `manual` — только карточка и кнопка
   «Опубликовать». Другого пути в PR у кода нет: построитель команды возвращает ровно
   `pr comment`, approve и request changes невозможны. Перед публикацией текст проходит маскировку
   секретов, а если детектор всё равно что-то видит — публикация отклоняется с причиной. Если
   подтверждённых находок нет, публиковать нечего: карточка пишет «замечаний нет».
9. **Где виден результат.** Карточка ревью во вкладке PR (находки по серьёзности, проверка, согласие,
   стоимость, ссылки на сессии, «Опубликовать», «Повторить»), короткая запись в `## Implementation
   Notes` связанной задачи (атомарно), событие `pr:reviewFinished` → уведомление нового вида
   `prReview`.

## Уточнения по факту реализации (TASK-81)

1. **Модули.** Чистые: `prSnapshot.ts` (`parseGhPrList`, `diffPrSnapshot`), `prReviewFormat.ts` (промпты,
   разбор оград, `dedupeFindings`, `applyVerdicts`, `buildPrComment`, `sanitizeForPublication`,
   `ghCommentArgs`). С зависимостями: `prWatcher.ts` (опрос и снимок), `prReviewService.ts` (оркестрация,
   записи, публикация), `prReviewApp.ts` (связывание с настоящими сервисами). Флот получил общий
   `buildRoleSlot` (им же пользуется `startRoleAgent`) и метку сессии `review`.
2. **Отложенный итог действия.** `reviewPr` — не одна сессия роя, а две последовательно, поэтому
   исполнитель действий возвращает `deferred` с обещанием итога, а о каждой сессии сообщает движку
   (`onSessionStarted`) — события этих сессий учитываются в причинности [[decision-52]] п. 5.
3. **Состояние `pending` фиксируется до возврата итога**, а запрос HITL уходит в фоне: запуск правила
   завершается сразу после ревью, не дожидаясь решения человека о публикации (до 24 часов).
4. **Дедупликация по живому прогону.** Одну ошибку два ревьюера описали на строках 6 и 7 разными
   словами: порога Жаккара 0.3 по тексту не хватило. Добавлены два правила: совпадающая цитата кода
   (`evidence`, Жаккар идентификаторов ≥ 0.6) и почти та же строка (±1) при пороге текста 0.15.
5. **Формат ответа повторяется последним абзацем промпта** («ответ без ограды не будет засчитан»):
   рассуждающая локальная модель без этого провела верное ревью, но вернула markdown-таблицы.
   Неразобранный ответ ревьюера не роняет ревью — ревьюер помечается ошибкой, остальные работают.
6. **Живая проверка (TASK-81.6)** — локальный bare-«origin» с `refs/pull/1/head`, подставной `gh`
   (на машине разработки GitHub CLI нет; публикация в настоящий PR не проверялась по решению
   пользователя). Ревьюеры Claude CLI (haiku) и API на удалённой Ollama (`ornith:35b`, усилие
   рассуждений `low`) нашли обе заложенные ошибки; проверяющий подтвердил их и отбросил неверное
   утверждение локальной модели («вернёт NaN» — на деле TypeError); worktree ревьюеров остались
   чистыми; публикация прошла через настоящую очередь HITL; стоимость ревью $0.07–0.08.

## Consequences

- Плюс: ревью любым движком и любой моделью, включая локальную, с транскриптом, HITL и
  бюджетом — тем же флотом, что и остальные агенты.
- Плюс: ложные находки отсекаются до человека; в чужой PR ничего не уходит без его решения.
- Минус: опрос — задержка до трёх минут и нагрузка на лимит GitHub API (один запрос на проект за
  опрос); вебхуки отложены.
- Минус: только GitHub через `gh`. GitLab (`glab`) — долг: `prService` не умеет его ни в списке, ни в
  диффе.
- Минус: три worktree на ревью (два ревьюера и проверяющий) занимают место до очистки веток
  `swarm/*`; сессии остаются в истории роя.
- Реализация: TASK-81. Опирается на [[decision-52]], [[decision-12]], [[decision-28]] (формат
  отчёта), [[decision-10]], [[decision-13]], [[decision-26]] п. 7, [[decision-7]].
