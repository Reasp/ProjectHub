## Context

Роли ProjectHub ([[decision-9]]) и HITL-контур с аудитом ([[decision-10]]) действуют, только когда агента
запускает ProjectHub: `buildEngineInvocation` превращает роль во флаги CLI, `--permission-prompt-tool` ведёт
запросы разрешений во встроенный MCP-сервер. Когда разработчик открывает `claude` или `codex` во встроенном
терминале (или в своём), ни роли, ни политика, ни аудит не работают. doc-10 (строка «Роли и политики вне
ProjectHub») ставит задачу сделать ProjectHub единым источником ролей и политик для всех поверхностей.

Факты из документации движков (проверено 2026-09-27, ссылки в TASK-77):

- **Claude Code** (установлен 2.1.280): субагенты `.claude/agents/<name>.md`, frontmatter `name`, `description`,
  `tools` (строка через запятую или список), `disallowedTools`, `model` (алиас `sonnet|opus|haiku|fable`, полный id
  или `inherit`), `permissionMode`, `maxTurns`, `effort`, тело — системный промпт. Хуки — в
  `.claude/settings.json` / `settings.local.json`: `hooks.<Event>[].matcher` + `hooks[].type: "command"`,
  `timeout` в секундах, по умолчанию 600. **По тайм-ауту вывод хука отбрасывается и инструмент выполняется** —
  это fail-open самого движка. PreToolUse получает `session_id`, `cwd`, `tool_name`, `tool_input`, `tool_use_id`,
  у субагента — `agent_type` (имя из frontmatter). Ответ `hookSpecificOutput.permissionDecision`:
  `allow` снимает собственный запрос разрешения CC (deny-правила CC продолжают действовать), `deny` отменяет вызов,
  `ask` показывает обычный запрос. Хук срабатывает до проверки прав, в любом режиме, в том числе в `claude -p`.
  PostToolUse получает `tool_response`, поля длительности нет; ошибка инструмента — отдельное событие
  `PostToolUseFailure`. Stop получает `stop_hook_active`. Есть и тип хука `http`, но переменные окружения в
  заголовках раскрываются только из `allowedEnvVars`, а поведение при недоступном адресе не настраивается.
- **Codex CLI** (не установлен и не оплачен, память paid-agent-tools): агенты `.codex/agents/<name>.toml` с
  обязательными `name`, `description`, `developer_instructions` и любыми ключами `config.toml` (`model`,
  `model_reasoning_effort`, `sandbox_mode`). Хуки — `.codex/hooks.json` проекта (формат как у Claude:
  `hooks.PreToolUse[].matcher` — регулярное выражение), загружаются только для доверенного слоя `.codex/`, и каждую
  новую команду хука пользователь подтверждает в `/hooks`. Надёжно документирован только отказ: `exit 2` с причиной в
  stderr или `permissionDecision: "deny"`. `allow` описан лишь вместе с `updatedInput`, `ask` «не поддержан» — Codex
  помечает хук упавшим и продолжает вызов. Текст патча `apply_patch` лежит в `tool_input.command`.
- **Google Antigravity**: субагенты `.agents/agents/<name>.md` и хуки `.agents/hooks.json` есть, но полный список
  имён инструментов для `tools` не опубликован, а **пустой `tools` означает «без инструментов»**; поведение хука при
  тайм-ауте и ненулевом коде выхода не описано. Угадывать имена инструментов значит выдать роли либо не те права,
  либо никаких.

Рассмотренные альтернативы:

1. **HTTP-хук Claude Code прямо на встроенный сервер.** Нет скрипта, но fail-open/fail-closed не настроить, Codex
   такого типа хука не имеет, а Bearer-токен пришлось бы пробрасывать через `allowedEnvVars`. Отвергнуто.
2. **Хук вызывает MCP-инструмент `permission_prompt` по SSE.** Долгое соединение ради одного вызова, а сам
   инструмент привязан к сессии AI Studio (`phSession`). Отвергнуто в пользу короткого REST-маршрута.
3. **Хук с основным токеном MCP (`PROJECTHUB_MCP_TOKEN`).** Этот токен даёт и `projecthub_approve_action`:
   агент в терминале, прочитав переменную окружения, мог бы одобрить собственный запрос. Отвергнуто: у хуков
   отдельный токен с правом только на маршрут хуков.
4. **Хуки в `.claude/settings.local.json` (не в git).** Тогда политика не едет с проектом ([[decision-7]] п. 3), а
   на другой машине хуки нужно ставить заново. Выбран общий `settings.json`: без токена хук ничего не делает.
5. **Писать поле-маркер во frontmatter субагента.** Реакция Claude Code на неизвестные ключи не документирована.
   Маркер пишется YAML-комментарием, который парсер отбрасывает.
6. **Экспорт в Antigravity по примерам из документации** (`view_file`, `grep_search`, `run_command`). Отвергнуто
   до публикации полного списка инструментов: см. факты выше.

## Decision

1. **Экспорт ролей — чистый модуль `roleExport.ts`.** Роль (с учётом слияния project > global > builtin) даёт:
   - **Claude Code** — `.claude/agents/<name>.md`, где `name` — slug роли с `_` → `-`. Поля: `name`,
     `description` (имя роли, первая фраза промпта, DoD), `tools` — по категориям `CLAUDE_TOOLS_BY_CATEGORY`
     (без `tools` у роли — поле не пишется, субагент наследует все инструменты; `Task` — прежнее имя `Agent`, в
     файл не пишется), `maxTurns` роли, `model`: явная модель роли, если это модель Claude (алиас или id
     `claude-…`), иначе первое звено тира роли для движка `claude-cli` из таблицы тиров ([[decision-44]]), иначе
     `inherit`. Вендорских дефолтов нет ([[decision-26]] п. 0). Тело — системный промпт роли. Права роли
     (`permissions`) в файл не пишутся: в ProjectHub запрет категории означает «спросить человека», а не «убрать
     инструмент», и это применяет слой хуков по имени субагента (п. 5).
   - **Codex** — `.codex/agents/<slug>.toml`: `name`, `description`, `developer_instructions` (промпт роли),
     `model` — явная модель роли, если роль привязана к `codex-cli`, иначе звено тира для `codex-cli`, иначе поле не
     пишется (наследование). `sandbox_mode`: `read-only`, если роль запрещает и запись, и команды, иначе
     `workspace-write`; `danger-full-access` не генерируется никогда. Категории `tools` Codex выразить не может —
     предупреждение в предпросмотре, как `unsupportedFeatures` в адаптере движков.
   - Роль, явно привязанная к другому движку (`engine: api`, `gemini-cli`, `codex-cli` для Claude и наоборот),
     не экспортируется в чужой движок: в предпросмотре — «пропущено: роль привязана к движку X». Роль без `engine`
     экспортируется во все поддерживаемые движки.
   - **Antigravity** в этой задаче не экспортируется (см. альтернативу 6); отдельная задача. Дополнено: экспорт и хуки
     Antigravity реализованы по живой проверке в TASK-106 — [[decision-62]].
2. **Идемпотентность и расхождения.** Первая строка сгенерированного файла — комментарий-маркер
   (`# projecthub:generated role=<slug> hash=<sha256[:16]>` во frontmatter md и в начале toml). `hash` считается от
   содержимого файла без строки маркера, с переводами строк, приведёнными к `\n` (git на Windows может вернуть CRLF).
   Решение по каждому файлу — чистая функция `planFileWrite`:
   - нет файла → `create`; файл совпадает с нужным → `unchanged`;
   - файл с маркером, `hash` совпадает с содержимым, но отличается от нужного → `update` (роль, тиры или
     генератор изменились — «устарел»);
   - файл с маркером, но содержимое не совпадает с `hash` → `conflict` («изменён вручную»), перезапись только по
     явному «перезаписать» в UI;
   - файл без маркера → `foreign`, не трогается никогда;
   - сгенерированный файл, роли которого больше нет → `orphan`, удаляется только по явному выбору.
   Синхронизация пишет файлы атомарно (tmp + rename). Индикатор в менеджере ролей — сумма `update`, `conflict`,
   `orphan`, `create` по проекту.
3. **Слой хуков.** Генерируется скрипт `.projecthub/hooks/projecthub-hook.mjs` (Node 18+, без зависимостей, с тем же
   маркером) и записи хуков:
   - Claude Code — в `.claude/settings.json` проекта: `PreToolUse`, `PostToolUse`, `PostToolUseFailure`, `Stop`,
     matcher `*`, команда `node "$CLAUDE_PROJECT_DIR/.projecthub/hooks/projecthub-hook.mjs" claude`, `timeout` —
     из настроек (по умолчанию 1800 с). Свои записи находятся по имени скрипта; чужие хуки и ключи не трогаются;
     невалидный JSON — `conflict`, файл не меняется.
   - Codex — в `.codex/hooks.json`: `PreToolUse`, `PostToolUse`, `Stop`, matcher `.*`, команда с путём от корня
     проекта. Живой проверки нет (Codex не оплачен); в UI и документации это сказано прямо.
   Скрипт читает stdin, отправляет `POST /api/hooks/event` встроенному серверу ProjectHub
   (`{ engine, projectDir, payload, budgetMs }`) и печатает готовый ответ, который строит чистый модуль
   `terminalHookProtocol.ts` (`{ exitCode, stdout, stderr }` в формате движка). Логики политики в скрипте нет.
4. **Авторизация.** Маршрут хуков принимает отдельный **токен хуков** (`ph_hook_…`, хранится в
   `secretStorageService`) или основной токен MCP; токен хуков не даёт доступа ни к SSE, ни к `/api/action`, ни к
   инструментам решений. Токен — только в переменной окружения `PROJECTHUB_HOOK_TOKEN`, адрес — в
   `PROJECTHUB_HOOK_URL`; в сгенерированные файлы они не пишутся (как правило 20 для `PROJECTHUB_MCP_TOKEN`).
   Встроенный терминал ProjectHub получает обе переменные и `PROJECTHUB_HOOK_FAIL_MODE` автоматически, если в
   проекте установлен скрипт хуков; для внешнего терминала UI даёт команду установки переменных. Проверки
   `Origin`/`Host` встроенного сервера действуют и для маршрута хуков.
5. **PreToolUse → политика и HITL.** Сервис `terminalHookService` определяет проект (зарегистрированный проект,
   содержащий `projectDir`; незарегистрированный — без решения), роль (по `agent_type` субагента, сгенерированного
   ProjectHub; у основной сессии роли нет) и считает вердикт той же политикой, что у агентов ProjectHub:
   `evaluateToolRequest(applyRolePermissions(глобальные правила AI Studio, права роли))`. Ответ движку:
   - `deny` политики → отказ с причиной; аудит — авто-решение с именем правила;
   - `allow` политики → **без решения**: движок применяет собственные правила, ProjectHub только сужает права и
     никогда не расширяет их сверх того, что решил человек; аудит — авто-решение;
   - `ask` → запрос в общую очередь `hitlService` (`origin: terminal`, движок, роль, команда или путь с диффом).
     Одобрение человека → `allow` для Claude Code (собственный запрос CC не показывается — двойного подтверждения
     нет); для Codex — без решения (Codex может спросить сам по своей политике — ограничение движка). Отказ или
     тайм-аут → `deny`.
   - `AskUserQuestion` в очередь не идёт — на вопрос отвечает человек в терминале.
   **Тайм-ауты:** движок по тайм-ауту хука выполняет инструмент, поэтому ожидание решения обязано закончиться
   раньше. Скрипт получает бюджет = `timeout` хука и сам отдаёт `deny` за 15 с до него; сервер ставит запросу HITL
   срок на 10 с раньше бюджета скрипта. Тайм-аут решения — это `deny` ([[decision-10]] п. 2), а не fail-open.
6. **PostToolUse → аудит с длительностью.** Сервер помнит момент решения по `tool_use_id` (час, затем забывает).
   PostToolUse / PostToolUseFailure пишут строку `outcome` (`executed | failed`) с новым полем аудита
   `durationMs` — от решения до завершения инструмента, без времени ожидания человека. Если PreToolUse не был
   виден (ProjectHub перезапускали), пишется авто-решение `post-only` и результат без длительности.
7. **Stop → уведомление и проверки.** Событие шины `agent:finished` (`origin: terminal`) идёт в обычные каналы
   уведомлений с дедупликацией по сессии. Проверки проекта по Stop настраиваются: `off` (по умолчанию — Stop
   приходит после каждого ответа модели), `notify` (прогнать блокирующие проверки проекта и сообщить о провале),
   `block` (при провале вернуть движку `decision: block` с причиной, чтобы агент продолжил; при
   `stop_hook_active` повторно не блокировать — защита от цикла).
8. **Fail-open по умолчанию, fail-closed настройкой.** Если ProjectHub не запущен, нет токена, токен не подходит или
   сервер не ответил в бюджет, скрипт в режиме `open` (по умолчанию) выходит с кодом 0 без решения и пишет строку в
   лог `PROJECTHUB_HOOK_LOG` (по умолчанию `<tmp>/projecthub-hook.log`, ротация 1 МБ); в режиме `closed`
   (`PROJECTHUB_HOOK_FAIL_MODE=closed`) PreToolUse отвечает отказом. PostToolUse и Stop не блокируют никогда. Режим
   задаётся окружением, а не файлом проекта: иначе fail-closed из git заблокировал бы коллег без ProjectHub.
   В лог не пишутся ни вход инструментов, ни токен.
9. **Настройки** — `<userData>/terminal-hooks.json` (`version`, `failMode`, `hookTimeoutSec` 60…3600, `stopChecks`),
   редактируются в менеджере ролей. `hookTimeoutSec` попадает в сгенерированные настройки движков, остальное
   применяется на стороне ProjectHub и терминала.
10. **Что коммитится в проект:** `.claude/agents/*.md`, `.codex/agents/*.toml`, `.projecthub/hooks/projecthub-hook.mjs`,
    записи хуков в `.claude/settings.json` и `.codex/hooks.json`. Не коммитится ничего: токен, адрес и режим отказа
    живут в окружении, настройки и аудит — в `userData`.
11. **Шаблон инфраструктуры.** `setup.mjs` и скилл `init-dev-project` (обе копии) знают про эти файлы: `setup.mjs`
    не трогает `.claude/agents`, `.codex/`, `.projecthub/hooks` и чужие ключи `.claude/settings.json`, а синхронизация
    ролей не трогает `.mcp.json`, `.agents/` и секции правил `sync-rules`. Генерирует файлы только ProjectHub.
12. **Границы.** Менеджер скиллов (п. 4 «Что сделать» TASK-77) и экспорт в Antigravity вынесены в отдельные задачи.
    `PermissionRequest` Codex не подключается, пока нельзя проверить, как он сочетается с PreToolUse.

## Consequences

- Плюс: роли ProjectHub работают как нативные субагенты в терминальных сессиях; HITL-очередь, телефон, Telegram и
  аудит видят действия терминальных агентов наравне с агентами ProjectHub; политика одна.
- Плюс: без ProjectHub (коллега, CI) хуки молча пропускают работу, а скрипт не требует зависимостей.
- Минус: каждый вызов инструмента в терминале — процесс Node и HTTP-запрос (десятки миллисекунд), аудит терминала
  растёт так же, как у агентов ProjectHub.
- Минус: модель субагента берётся из таблицы тиров машины, которая выполнила синхронизацию; на другой машине файл
  может ссылаться на другую модель тира. Файлы с явным `inherit` этого не имеют.
- Минус: в Codex одобрение в ProjectHub не снимает собственный запрос Codex; хуки Codex и формат агентов не проверены
  вживую.
- Риск: агент в терминале видит `PROJECTHUB_HOOK_TOKEN` и может присылать события хуков от своего имени — максимум
  создать лишний запрос в очередь или строку аудита с `origin: terminal`; одобрить что-либо этим токеном нельзя.
- Реализация: TASK-77.

## Реализация и уточнения (TASK-77, 2026-09-27)

Решение принято и реализовано. Модули: `roleExport.ts` (маппинг, маркер, `planFileWrite`, слияние хуков),
`terminalHookProtocol.ts` (разбор входа, ответ движку, настройки), `terminalHookScript.ts` (исходник скрипта),
`terminalHookService.ts` (политика, HITL, аудит, Stop, токен хуков), `roleSyncService.ts` (план и запись), маршрут
`POST /api/hooks/event` в `mcpServerService`, провайдер окружения встроенного терминала в `ptyService`, панель
«Синхронизация в проект» в менеджере ролей (`RoleSyncPanel`), источник `terminal` и поле `durationMs` в аудите и
Центре решений.

Живая проверка (Claude Code 2.1.280, Windows 10, модель haiku, временный git-проект, встроенный сервер на отдельном
порту, решения через `hitlService.decide`):

1. Команда хука `node "$CLAUDE_PROJECT_DIR/.projecthub/hooks/projecthub-hook.mjs" claude --budget N` из
   `.claude/settings.json` проекта работает на Windows; в `claude -p` хуки проекта срабатывают без отдельного
   подтверждения доверия.
2. `echo` при политике `allow` — без решения, Claude Code выполнил команду по своему `--allowedTools`; в аудите
   авто-решение `auto-command` и результат с `durationMs` (840 мс).
3. `git push origin main` (deny-список команд → `ask`) ушёл в очередь HITL с `origin: terminal` и сроком 275 с при
   тайм-ауте хука 300 с. После одобрения человеком Claude Code выполнил вызов **без собственного запроса**, хотя команды
   не было в `--allowedTools`: `permissionDecision: allow` снимает запрос движка. Неудачный push пришёл событием
   `PostToolUseFailure` (`error: "Exit code 128 …"`) и записан как `failed` с длительностью.
4. Отказ человека с комментарием дошёл до модели: «Отклонено в ProjectHub: нельзя пушить».
5. Сгенерированный `.claude/agents/reviewer.md` (модель из тира) распознан: вызовы субагента пришли с
   `agent_type: "reviewer"`, аудит записал `role: reviewer`, `agentName: "Claude Code · reviewer"`, чтение —
   авто-правило `auto-read`; запуск субагента — `auto-subagent` у инструмента `Agent`.
6. ProjectHub остановлен: работа не заблокирована (fail-open), в логе хука три строки `ECONNREFUSED`
   (PreToolUse, PostToolUse, Stop).
7. Stop каждого запуска дал событие `agent:finished` с `origin: terminal`.

Уточнения по ходу реализации:

- В текущем Claude Code инструмент подагентов называется `Agent`; `CLAUDE_TOOLS_BY_CATEGORY.subagent` теперь
  `['Agent', 'Task']`, поэтому `--allowedTools` агентов ProjectHub с категорией `subagent` тоже получает `Agent`.
- Скрипт различает «ProjectHub недоступен» (нет соединения, нет токена, 401 → режим отказа) и «сервер принял запрос,
  но не ответил в бюджет» — второе всегда отказ PreToolUse, иначе тайм-аут решения стал бы разрешением.
- Обрыв соединения скрипта (движок завершил хук) снимает запрос с очереди HITL, а не оставляет его до тайм-аута.
