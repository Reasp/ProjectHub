## Context

doc-6 §4.2 предложил аудит зависимостей и сканер секретов, doc-10 записал это пробелом «безопасность цепочки
поставок» (TASK-73). Агент, который пишет код в worktree, может добавить в проект ключ или пакет, а ProjectHub сейчас
вливает его результат (Pick Winner, сборка из файлов, авто-мердж [[decision-12]]) без взгляда на это. Коммит из
GitInspector и с телефона (Remote Control RPC `git_commit`) тоже ничего не проверяет.

Факты (проверено 2026-09-27, Windows 10, npm 10.9.2, Node 22.16):

- **`npm audit --json`** на временном проекте (`lodash@4.17.20`, `minimist@1.2.5`): `auditReportVersion: 2`,
  `vulnerabilities` — словарь по имени пакета с `severity`, `isDirect`, `via`, `effects`, `range`, `nodes`,
  `fixAvailable` (`{name, version, isSemVerMajor}` или `true/false`); `via` — массив, где объект — advisory
  (`source`, `title`, `url` на GHSA, `severity`, `cwe`, `cvss`, `range`), а строка — имя пакета, через который пришла
  уязвимость (транзитивная, проверено на `mkdirp@0.5.1` → `minimist`). `metadata.vulnerabilities` — счётчики
  `info/low/moderate/high/critical/total`. Код возврата 1 при находках и 0 без них — это не ошибка.
- Без lock-файла: `{"error":{"code":"ENOLOCK",…}}`, код 1. При недоступном registry: `{"message":"request to … failed,
  reason: connect ECONNREFUSED …","error":{"summary":"","detail":""}}`, код 1.
- **`pip-audit` 2.10.1** (поставлен во временный venv, на машине его нет): `{"dependencies":[{name, version, vulns:[{id,
  fix_versions, aliases, description}]}], "fixes":[]}`, уровня критичности нет, один и тот же `id` встречается дважды.
  Обычный `-r requirements.txt` ставит пакеты во временное окружение — сборка sdist исполняет чужой код. Режим
  `--no-deps --disable-pip` ничего не ставит (0,6 с), но работает только с точными пинами `==`: на `flask>=0.12` stdout
  пуст, в stderr «not pinned to an exact version».
- **`cargo audit`** — cargo на машине не установлен, формат вывода проверить нечем.
- Дата публикации версии есть только в полном документе пакета (`time`), не в сокращённом
  (`application/vnd.npm.install-v1+json`). `npm view <имя>@<версия> time --json` — около 0,9 с, берёт registry, прокси
  и авторизацию из `.npmrc` пользователя; несуществующий пакет — `{"error":{"code":"E404",…}}`, код 1.
- Детектор секретов уже есть: `secretPatterns.detectSecrets` ([[decision-51]] п. 5) — AWS, `sk-`/`sk-ant-`, GitHub,
  Slack, Google, Hugging Face, PEM, JWT, пароли в URL, Bearer, `ИМЯ=значение`. Шаблона токена Telegram-бота нет.
- Слияние кандидата в базовую ветку — только `pickWinner` (ручной Pick Winner и `maybeAutoMerge`); сборка из файлов —
  `composeFromCandidates` (`git checkout <ветка> -- <файлы>`). GitNexus impact: `pickWinner` и `commitChanges` — HIGH
  (IPC, авто-мердж, RPC Remote Control), `detectSecrets`, `scoreCandidates`, `composeFromCandidates` — LOW.
- Хуки терминала ([[decision-54]]) уже получают `Bash`-команды Claude Code/Codex в `preToolUse` с рабочим каталогом.

Рассмотренные и отвергнутые альтернативы:

1. **Второй детектор секретов** (свой набор regex или gitleaks/trufflehog как бинарь). Два источника правды расходятся;
   внешний бинарь есть не у всех и требует установки. Детектор один — `detectSecrets`, диффу нужен только разбор патча.
2. **Жёсткий отказ коммита с секретом.** Ложные срабатывания (фейковые ключи в тестах) выгнали бы человека в терминал,
   где проверки нет вовсе. Человек у экрана решает сам, решение остаётся в аудите.
3. **Git pre-commit hook в проекте.** Трогает `.git/hooks` чужого репозитория, конфликтует с хуками проекта (шаблон
   ставит свои git-hooks) и не видит слияние кандидатов. Проверка стоит там, где ProjectHub сам делает коммит или
   слияние, и в хуке терминала, где он видит команду.
4. **Секреты — блокирующий критерий Arena.** [[decision-20]] п. 5 оставляет блокирующими только проверки. Ложное
   срабатывание не должно лишать кандидата рекомендации — жёсткость переносится на слияние (HITL).
5. **Автоисключение тест-фикстур по пути** (`test/`, `fixtures/`). Реальные ключи в тестах — частый путь утечки.
   Исключения задаются явно и видны в счётчике подавленных находок.
6. **Прямой HTTP-запрос к registry.npmjs.org** за датой публикации. Игнорирует `.npmrc` (приватный registry, прокси,
   токен) и отправил бы имена внутренних пакетов в публичный registry.
7. **Аудит при открытии проекта или по таймеру без правила.** Исходящий вызов без действия человека ([[decision-7]]
   п. 4). Регулярность — только правилом Automations, которое человек создал сам.
8. **Создавать lock-файл за пользователя** (`npm i --package-lock-only`) и **обычный `pip-audit -r`** — оба меняют
   окружение или исполняют код пакетов ради отчёта.
9. **Автосоздание задач Backlog по находкам из Automations.** Каждый прогон плодил бы дубли; задачу создаёт человек
   кнопкой, уведомление приходит само.
10. **Отчёт аудита в проекте** (`.projecthub/`). Уехал бы в git и в worktree агентов.

## Decision

1. **Чистые модули с тестами на реальных выводах** (правило 17):
   - `dependencyAudit.ts` — разбор `npm audit --json` (v2) и `pip-audit -f json`, классификация ошибок запуска
     (`ENOLOCK`, сеть, чужой формат), сводка по уровням, «новые находки» относительно прошлого отчёта;
   - `diffSecretScan.ts` — скан унифицированного диффа детектором `detectSecrets`;
   - `dependencyDiff.ts` — изменения зависимостей между двумя версиями `package.json`, новые записи lock-файла,
     добавленные строки `requirements*.txt`, флаги риска по метаданным registry;
   - компонент `security` в `arenaScoring.ts`.
   В `secretPatterns` добавляется вид `telegram_token` (`\d{8,10}:[A-Za-z0-9_-]{35}`) — он действует и для памяти.

2. **Аудит зависимостей проекта.**
   - **npm:** `package-lock.json` или `npm-shrinkwrap.json` в корне → `npm audit --json`. Без lock-файла — статус
     `no_lockfile` с подсказкой команды; сам ProjectHub lock не создаёт. Рабочие области npm покрываются одним lock в
     корне; вложенные независимые проекты без workspaces не сканируются. `yarn.lock`/`pnpm-lock.yaml` без
     `package-lock.json` — статус `unsupported` (их формат аудита не проверен).
   - **Python:** только если `pip-audit` доступен (`pip-audit` в PATH или `python -m pip_audit`) и в корне есть
     `requirements*.txt`: `pip-audit -r <файл> --no-deps --disable-pip -f json` — без установки пакетов. Незакреплённые
     требования — статус `unsupported` с причиной «нужны точные версии ==». Уровень — `unknown`, дубли `id` схлопываются.
   - **Rust:** при `Cargo.lock` — статус `unsupported` («формат cargo audit не поддержан»), до проверки на живом выводе.
   - Нет инструмента — `not_installed` («нет данных»), не ошибка. Нет сети — `error` с видом `network`; прошлый отчёт
     остаётся и помечается устаревшим.
   - Запуск без аргументов из данных проекта, тайм-аут 120 с, stdout до 32 МБ, `CI=1`; один аудит проекта одновременно,
     повтор не чаще раза в 10 минут (иначе возвращается кэш с пометкой).
   - Находка — пакет, уровень, прямой или транзитивный, advisories (id GHSA/PYSEC, заголовок, ссылка, диапазон), fix.
     Уровни: `critical`, `high`, `moderate`, `low`, `info`, `unknown`.
   - Хранение — `<userData>/security/<sha1(корень)[:12]>.json` (последний отчёт по экосистемам, версия схемы,
     созданные задачи), не в проекте.
   - «Создать задачу» — задача Backlog «Уязвимость `<пакет>`: `<заголовок>`» с label `security`, в описании — advisories,
     ссылки и версия с исправлением (`createBacklogTaskFile`). Созданная задача запоминается по пакету, повторная кнопка
     показывает её id.

3. **Сканер секретов на диффе.**
   - Сканируются только **добавленные** строки (`+`, не `+++`); номер строки — из заголовка hunk. Удалённые строки не
     сканируются: удаление секрета — не утечка, а то, что уже в истории, — вне охвата.
   - Новый файл `.env` или `.env.*` в диффе — находка `env_file`, кроме `.env.example`, `.sample`, `.template`, `.dist`;
     содержимое любых файлов, включая примеры, проходит через детектор.
   - Бинарные файлы пропускаются; из строки длиннее 4000 символов сканируется начало; сверх 2 МБ добавленного текста —
     `truncated`.
   - Находка — вид, файл, строка. Значение секрета не уходит ни в UI, ни в аудит, ни в уведомления, ни в лог.
   - Исключения: `security.secretScan.allowPaths` (glob) в `.projecthub.json` **основного дерева** проекта (не из
     worktree агента) и маркер `projecthub:allow-secret` на той же строке. Маркер действует для изменений человека
     (GitInspector, терминал); в диффах агентов игнорируется — агент не может сам себе разрешить. Подавленные находки
     показываются числом.

4. **Коммит.**
   - Проверка — в main-процессе, в `git:commit` (рендерер её не обойдёт): после `stageAll` берётся `git diff --cached`.
     Есть находки — коммит не выполняется, ответ `{ ok: false, reason: 'secrets', findings, treeHash }`.
   - GitInspector показывает находки диалогом (`DialogHost`, `z-[10001]`, [[decision-17]]) с кнопками «Отмена» и
     «Закоммитить всё равно». Повтор идёт с `acknowledgeSecrets: treeHash`: main пересчитывает `git write-tree`
     индекса; совпало — коммит и запись в аудит HITL `decidedBy: local`, правило `secret-scan-override`, детали — виды и
     файлы; не совпало (индекс изменился) — проверка заново.
   - Remote Control RPC `git_commit`: тот же скан; при находках — отказ с видами и файлами, «всё равно» с телефона нет.
   - Терминальные сессии ([[decision-54]]): PreToolUse `Bash` с `git commit` → скан staged-диффа в `cwd` (с `-a`/`--all` —
     ещё и неиндексированных изменений отслеживаемых файлов). Находки поднимают `allow` до `ask` (правило `secret-scan`),
     `deny` роли остаётся `deny`. Ошибка скана оставляет вердикт политики (fail-open, как у хуков).

5. **Слот Swarm.** При расчёте диффа слота сохраняется `agent.security`:
   - секреты — по полному патчу до усечения при сохранении;
   - зависимости — для каждого `package.json` из диффа сравниваются версия базы (`git show <база>:<путь>`) и файл
     worktree по секциям `dependencies`, `devDependencies`, `optionalDependencies`, `peerDependencies` (добавлено,
     изменена версия, удалено); для `package-lock.json` — число новых записей `packages` (транзитивные);
     для `requirements*.txt` — добавленные требования. Другие манифесты не разбираются;
   - метаданные registry для добавленных и изменённых npm-пакетов (п. 9): `npm view <имя>@<версия> time deprecated
     --json`. Имя и версия приходят из диффа агента, поэтому до запуска проверяются строгим шаблоном имени npm и версии.
     Флаги: `not_found` (E404 — выдуманное имя или опечатка), `recent` (версия моложе 7 дней), `young` (пакет моложе
     30 дней), `deprecated`. Кэш `имя@версия` — `<userData>/security/registry-cache.json` на 7 дней; до 20 пакетов на
     слот, 4 запроса одновременно, тайм-аут 15 с;
   - карточка кандидата показывает блок «Безопасность»: секреты (вид, файл:строка), «Добавлены зависимости» (имя,
     версия, дата публикации, флаги), число новых пакетов в lock.

6. **Arena.**
   - Новый компонент балла `security`, вес по умолчанию 10. Шкала абсолютная, не когортная: 1 — чисто; 0 — секреты;
     0.5 — секретов нет, но есть пакет с флагом риска; `unknown` 0.5 — скана не было (нет диффа, [[decision-20]] п. 4).
     Добавление зависимости само по себе не штрафуется.
   - Не блокирующий критерий (альтернатива 4). Авто-мердж запрещён, если у кандидата есть секреты или любые новые либо
     изменённые зависимости: причина «нужно решение человека».
   - Ревьюер получает сводку безопасности текстом: виды и файлы секретов, новые пакеты с флагами.

7. **HITL при слиянии.** Pick Winner и сборка из файлов, если у кандидата (для сборки — в выбранных файлах) есть секреты
   или новые либо изменённые зависимости, ставят запрос в общую очередь HITL ([[decision-10]]): тип `command`, заголовок
   «Слить кандидата …: секретов N, пакетов M», в `details` — список без значений; тайм-аут 30 минут. Одобрение с любого
   канала — слияние; отказ или тайм-аут — слияние не выполняется, причина возвращается в UI. Перед запросом состояние
   безопасности пересчитывается, если ветка кандидата сдвинулась.

8. **Automations** ([[decision-52]]): новое действие `auditDependencies` (не агентное, без бюджета) — аудит проекта
   правила; итог `success` со сводкой или `failed` при ошибке инструмента; новые находки уровня не ниже `minSeverity`
   (по умолчанию `high`) публикуют событие `security:finding`. Лимиты правила общие, интервал 10 минут из п. 2 действует
   и здесь. Задачи автоматически не создаются.

9. **Сеть** ([[decision-7]] п. 4). Этот ADR разрешает исходящие вызовы: `npm audit` (дерево имён и версий зависимостей
   уходит в registry из npm-настроек пользователя), `pip-audit` (PyPI) и `npm view` для пакетов, добавленных агентом.
   Аудит запускается только кнопкой или правилом Automations. `npm view` работает при расчёте диффа слота; выключатель
   `registryLookups` в `<userData>/security/settings.json` отключает его, и даты публикации показываются как «не
   запрашивались». При открытии проекта показывается кэш, без сети.

10. **Уведомление.** Событие шины `security:finding` (`projectPath`, `source: audit | secrets | dependencies`, уровень,
    сводка, `swarmId`/`agentId` для слота). Вид `securityFinding` в матрице каналов, по умолчанию трей, ОС, Telegram,
    Remote. Для слота публикуется один раз на агента и состояние. Значений секретов в тексте нет. Клик ведёт во вкладку
    «Безопасность» проекта или в сессию Swarm.

## Consequences

- Плюс: агентский дифф с ключом или новым пакетом больше не вливается молча — ни вручную, ни авто-мерджем; решение
  остаётся в аудите.
- Плюс: один детектор секретов для памяти, коммитов, хуков и Arena; значения секретов нигде не сохраняются.
- Плюс: `not_found` ловит выдуманные моделью пакеты до установки.
- Минус: скан только добавленных строк не находит секрет, который уже был в истории, а перенос строки находит заново.
- Минус: эвристики детектора ([[decision-51]]): экзотический формат пройдёт, длинный буквенно-цифровой идентификатор
  рядом с `key=` сработает ложно — для этого `allowPaths` и маркер.
- Минус: аудит только по npm-lock и закреплённым `requirements*.txt`; yarn, pnpm, cargo — «нет данных».
- Минус: `npm audit` отправляет список зависимостей в registry — это цена аудита; без явного действия он не выполняется.
- Минус: новый компонент меняет итоговые баллы по сравнению с прежними прогонами (они и так несравнимы, [[decision-20]] п. 3).
- Долг: вложенные проекты без workspaces, форматы `pnpm audit`, `yarn npm audit`, `cargo audit`; скан истории ветки
  кандидата по коммитам; уведомление о секретах в памяти.
- Реализация: TASK-73. Связано: [[decision-7]], [[decision-8]], [[decision-10]], [[decision-12]], [[decision-17]],
  [[decision-20]], [[decision-51]], [[decision-52]], [[decision-54]].

## Реализация и уточнения (TASK-73, 2026-09-27)

Решение реализовано. Модули: чистые `dependencyAudit.ts` (npm audit v2, pip-audit, цели аудита, новые находки, задача из
находки), `diffSecretScan.ts` (скан патча, glob `allowPaths`, маскировка патча), `dependencyDiff.ts` (манифесты, lock,
requirements, `npm view`, флаги риска), `slotSecurity.ts` (отчёт слота, вход балла, текст HITL), `terminalCommitScan.ts`
(`git commit` в команде терминала); сервисы `securityHealthService.ts` (аудит, кэш, настройки, registry), `commitSecretGuard.ts`
(коммит окна и телефона); IPC `security:*`, вкладка «Безопасность», блок `SlotSecurityPanel` в карточке кандидата, действие
`auditDependencies`, вид уведомления `securityFinding`. Тесты — на выводах, снятых с живых запусков (`tests/unit/fixtures/security`).

Уточнения по ходу:

1. **Интервал 10 минут — только для Automations.** Кнопка «Запустить аудит» всегда выполняет аудит: человек нажимает её,
   когда хочет свежий результат. Правило cron в пределах интервала получает кэш с пометкой в журнале.
2. **Порог `unknown`.** pip-audit уровня не сообщает; для порога уведомления `unknown` считается как `high` (проходит любой
   порог, кроме `critical`) — лучше лишнее уведомление, чем молча пропущенная уязвимость Python-пакета.
3. **Ответ `npm view` бывает двух форм.** С `deprecated` — `{ time, deprecated }`, без него — сама карта `time`
   (проверено на `minimist@1.2.8`). Разбор понимает обе.
4. **Хук терминала и `git add && git commit`.** На момент PreToolUse индекс ещё не содержит того, что добавит команда.
   Для `git commit -a/--all/-am` и цепочек с `git add`/`rm`/`mv` сканируются изменения отслеживаемых файлов от HEAD и
   неотслеживаемые файлы (без `.gitignore`, текстовые до 1 МБ, до 200 файлов); иначе — staged-дифф. Аргументы разбираются с
   учётом кавычек (`-m "fix all"` не флаг `-a`), путь к `git.exe` в кавычках распознаётся.
5. **Ревьюер не получает значения секретов.** Если сканер нашёл секреты, дифф в промпте LLM-ревьюера маскируется
   (`maskSecretsInPatch`: значения — `***`, тело PEM — `***` построчно), и ревьюер получает сводку безопасности текстом.
   Без находок дифф уходит как раньше.
6. **Одно уведомление на агента.** При секретах ключ уведомления зависит только от секретов: флаги registry, пришедшие
