## Context

`npm run build` (и `pack:win`, который его вызывает) с 2026-09-27 регулярно падал на двух файлах: `checkpointGit.test.ts` (тайм-аут теста 5 с или хука 10 с, затем EBUSY/ENOTEMPTY при удалении временного репозитория) и `agentFleetOrphans.test.ts` (EBUSY на каталоге `bg-runGeminiCliAgent` в `afterAll`). Отдельные прогоны `vitest` при этом были зелёными, поэтому подозревалась вложенная cmd-цепочка npm. Разбор в TASK-108:

1. **Цепочка ни при чём.** Тот же `npm run build` под env-tools (скрытый PowerShell, вывод в файл) прошёл целиком: 174 файла / 1975 тестов за 61 с, трансформация 7 %. А отдельный `npx vitest run` этих двух файлов под искусственной нагрузкой (20 busy-процессов на 16 логических ядрах) падает теми же сигнатурами: 9 из 15 тестов. В прошлой сессии трансформация занимала ~160 с — машина была перегружена сторонними процессами; зависимость от способа запуска была совпадением по времени.
2. **checkpointGit.** Один тест — 25–50 запусков git (измерено через `GIT_TRACE2_EVENT`: откат — 48, CheckpointService — 51; `beforeEach` — ещё ~10). Без нагрузки самый тяжёлый тест идёт 1.4 с, в полном прогоне рядом с другими воркерами — 2.45 с, то есть половина бюджета 5 с уходит на собственную параллельность набора. По тайм-ауту vitest переходит к `afterEach`, а тело теста продолжает гонять git в том же каталоге — отсюда EBUSY/ENOTEMPTY. EBUSY здесь следствие тайм-аута, а не отдельная причина.
3. **agentFleetOrphans — кто держит каталог.** В момент EBUSY среди процессов, созданных за время прогона, нет ни одного процесса теста (снимок WMI; `handle64` из Sysinternals к моменту снимка уже ничего не находит — каталог освобождается сам за 0.1–5 с). `waitDead` в `afterEach` всегда возвращал «мёртв» за 0 мс. Причина — семантика libuv на Windows: `process.kill(pid, 0)` проверяет `GetExitCodeProcess`, а код выхода выставляется сразу при `TerminateProcess`, до того как ядро закроет таблицу дескрипторов процесса, включая дескриптор текущего каталога. Под нагрузкой это закрытие запаздывает на секунды. A/B-проверка: если фоновый потомок запускается с cwd вне каталога агента, EBUSY исчезает (0 из 3 прогонов под нагрузкой против 6 из 6). Падает всегда последний каталог — его потомка убивает `afterEach` непосредственно перед `afterAll`; встроенные повторы `fs.rmSync` (5 × 200 мс, линейно, ~3 с) не покрывают задержку.
4. Отвергнутые гипотезы: conhost у detached-потомка (у `DETACHED_PROCESS` нет консоли; `handle64` conhost не показывал), антивирус (Defender и сторонние AV не установлены, индексатор остановлен), git-процессы в `agentFleetOrphans` (их там нет).
5. **Попутно найдено.** Тесты подменяют `USERPROFILE` временным домом (decision-29). В нём не было `AppData\Local`, а .NET `Environment.GetFolderPath` для несуществующей папки возвращает пустую строку — PowerShell, запущенный тестами с cwd = корень проекта, записал кэш анализа модулей в `F:\ProjectHub\Microsoft\Windows\PowerShell\ModuleAnalysisCache`.

Рассмотренные альтернативы:

- Поднять тайм-ауты всего набора (`testTimeout` в `vitest.config.ts`) — скрыло бы зависания в быстрых тестах; тяжёлых файлов с реальными процессами немного, и почти у всех тайм-ауты уже явные.
- Изоляция тяжёлых файлов (`poolOptions.forks.singleFork`, отдельный проект vitest с `maxWorkers: 1`) — лечит симптом нагрузки ценой длительности всего набора; при разборе выяснилось, что EBUSY — не про параллельность, а про семантику завершения процесса.
- Развести lint и test в `build` — цепочка не причина (п. 1).
- Ждать реальной смерти процесса вместо `kill(pid, 0)` — из Node нет API ожидания объекта процесса по PID для не-дочернего процесса; запуск PowerShell `Wait-Process` под нагрузкой сам идёт секунды.
- Поднять `LIST_PROCESSES_TIMEOUT_MS` в продукте — это UX-компромисс остановки агента; при нагрузке выше числа ядер снимок WMI может не уложиться в 15 с, и тест «добивает потомка» честно падает. Это реальный предел продукта, его не маскируем.

## Decision

1. Тест, который запускает реальные процессы (git, оболочки, CLI), задаёт тайм-аут явно, с обоснованием в комментарии от числа запусков, а не полагается на значения vitest по умолчанию (5 с тест, 10 с хук). Для файла целиком — `vi.setConfig({ testTimeout, hookTimeout })` в начале файла; `checkpointGit.test.ts` — 30 с.
2. Временные каталоги, которые могли быть cwd запущенных процессов, удаляются хелпером `tests/helpers/removeTempDir.ts`: повтор при EBUSY/ENOTEMPTY/EPERM/EACCES с растущей паузой (50 мс → 1 с) до дедлайна (30 с по умолчанию). Не удалось к дедлайну — ошибка: каталог держит живой процесс, это утечка.
3. «Процесс мёртв» по `process.kill(pid, 0)` не означает, что ОС освободила его cwd и файлы. Проверки удаления каталогов после kill не строятся на этом допущении.
4. Временные границы в ассертах выводятся из констант продукта, а не из времени на свободной машине: граница остановки CLI-агента — `LIST_PROCESSES_TIMEOUT_MS + CHILD_CLOSE_GRACE_MS + 5 с` (константа тайм-аута снимка процессов вынесена из `listWindowsProcesses` и экспортируется из `processSweep.ts`, поведение не меняется).
5. Временный дом тестов (decision-29) создаётся с `AppData/Local` и `AppData/Roaming`, чтобы известные папки Windows вычислялись внутрь него, а не в cwd.
6. Конфигурация пула vitest и цепочка `npm run build` не меняются.

## Consequences

- `npm run build` / `pack:win` больше не падает на этих файлах от кратковременной перегрузки машины; под нагрузкой ниже числа ядер (12 busy-процессов на 16 ядрах) — зелено, под насыщающей (20 на 16) EBUSY и тайм-ауты `checkpointGit` исчезли.
- Под насыщающей нагрузкой может падать проверка «добивает потомка» в `agentFleetOrphans`: снимок WMI дольше 15 с, и обход потомков сдаётся по дизайну decision-37. Это сигнал о пределе продукта, а не флейк.
- Полный набор под нагрузкой, превышающей число ядер, по-прежнему нестабилен во многих файлах — ни один тайм-аут это не лечит; `pack:win` на перегруженной машине стоит запускать после разгрузки.
- Новый тест с реальными процессами обязан следовать п. 1–3; хелпер покрыт `tests/unit/removeTempDir.test.ts`.
- Реализация — TASK-108. Связано: [[decision-29]], [[decision-37]].
