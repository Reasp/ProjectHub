## Context

Реестр env-tools `.env-state/processes.json` хранил для записи только `pid`, `command`, `cwd` и `startedAt`. Жив ли процесс, `scripts/env/state.mjs` → `isAlive(pid)` определял через `process.kill(pid, 0)`, а это проверка «есть ли процесс с таким pid», а не «тот ли это процесс». ОС переиспользует pid, и запись из прошлой сессии начинает указывать на чужой процесс. Отсюда три ошибки:

- `list_processes` показывает такую запись как «работает»;
- `start_process` с тем же именем отказывает как дубликату;
- `stop_process` выполняет `taskkill /T /F` по чужому дереву процессов.

Диагностика на реестре хаба 2026-09-28 (TASK-110): 86 записей, `kill(pid, 0)` считает живыми 3. Из них `pack-win-72c` (pid 28024) указывала на `conhost.exe`, `shot-81b` (pid 38880) — на `backlog.exe`, MCP-сервер Backlog текущей сессии агента. `stop_process shot-81b` убил бы его. Записи копились с 2026-09-18: чистки не было, мёртвые записи никто не удалял.

Замеры (Windows 10 19045, PowerShell 5.1, 16 логических ядер):

- пакетный `Get-CimInstance Win32_Process` с фильтром по pid — ~480 мс, `Get-Process -Id a,b,c` — ~240 мс, пустой запуск `powershell.exe` — ~100 мс;
- `Process.StartTime` и CIM `Win32_Process.CreationDate` совпали до миллисекунды у всех 650 процессов системы; у двух системных процессов `StartTime` недоступен.

Рассмотренные варианты идентичности:

1. **Время создания процесса по ОС** — выбрано. Оно однозначно определяет процесс: у переиспользованного pid оно другое. На Windows его отдаёт сама обёртка без дополнительных вызовов, на POSIX — `ps -o lstart=`.
2. **Имя образа** (`powershell.exe` для обёртки на Windows). Отвергнуто: pid может достаться другому экземпляру PowerShell, а на POSIX образ — это `sh` или сама команда.
3. **Отметка `Date.now()` перед spawn и окно допуска**, как у обхода потомков в [[decision-37]]. Отвергнуто для реестра: окно в секунды при нагрузке ([[decision-57]]) хуже точного значения, которое обёртка может записать сама.

Варианты чистки: отдельный инструмент `prune_processes` или удаление при `list_processes`. Отдельный инструмент никто не вызывал бы: записи копились именно потому, что чистка не встроена в обычную работу.

## Decision

1. **Поле `pidCreatedAt`** в записи реестра — время создания процесса по данным ОС, мс Unix (те же единицы, что `createdAt` в `electron/services/processSweep.ts`).
   - Windows: обёртка `.env-state/wrappers/<name>.ps1` пишет в pid-файл строку `pid,ms` из `[Diagnostics.Process]::GetCurrentProcess().StartTime`. Файл пишется во временный и переименовывается, чтобы ожидающий Node не прочитал его наполовину. Запуск обёртки прежний — `cmd /c start /b` ([[decision-58]]).
   - POSIX: сразу после spawn — `ps -o pid=,lstart= -p <pid>` с `LC_ALL=C` (точность 1 с).
2. **Проверка — одним запросом на вызов инструмента.** Сначала `kill(pid, 0)` отсекает свободные pid. Только по оставшимся выполняется один `Get-Process -Id a,b,c` (Windows) или `ps -p a,b,c` (POSIX). Время сравнивается с тем же источником, что и при записи, с допуском `IDENTITY_TOLERANCE_MS` = 1000 мс (из-за секундной точности `lstart`). Если живых pid нет, PowerShell не запускается.
3. **Три статуса записи** (`entryStatus` в `scripts/env/state.mjs`):
   - `running` — время старта совпало;
   - `dead` — процесса нет, или pid занят процессом с другим временем старта;
   - `unknown` — pid занят, но сопоставить нельзя: запись без `pidCreatedAt` или ОС не отдала время старта.
4. **Старые записи без `pidCreatedAt`.** `startedAt` записывается после получения pid, поэтому настоящий процесс создан не позже него. Если процесс с этим pid создан позже `startedAt` (с допуском), pid точно переиспользован — статус `dead`. Иначе статус `unknown`.
5. **Поведение инструментов:**
   - `stop_process` убивает дерево только при `running`. При `dead` и `unknown` он лишь удаляет запись и сообщает, почему процесс не останавливался. Если запрос к ОС не удался, `stop_process` возвращает ошибку и запись сохраняется: без проверки убивать нельзя, а молча забывать процесс — тоже.
   - `start_process` считает дубликатом только `running`.
   - `list_processes` показывает статус; `alive` остаётся синонимом `running` для совместимости.
6. **Чистка:** `list_processes` удаляет записи со статусом `dead`, у которых не было активности дольше `PRUNE_AFTER_MS` = 7 дней. Активность — это `max(startedAt, mtime лога)`. Вместе с записью удаляются лог и файлы обёртки. Недавние мёртвые записи остаются: «НЕ работает» и `tail_log` подсказывают агенту, что его dev-сервер упал. Записи `unknown` автоматически не удаляются, их убирает `stop_process`. Перед записью реестр перечитывается, и удаляются только записи с теми же `pid` и `startedAt`: другая сессия могла за это время перезапустить процесс под тем же именем.
7. `startProcess` и `stopProcess` тоже перечитывают реестр перед записью (`updateRegistry`), чтобы не затирать записи параллельной сессии env-tools, сделанные за время ожидания pid-файла.

## Consequences

- Чужой процесс с переиспользованным pid больше не выглядит работающим, не блокирует `start_process` и не убивается `stop_process`. Это покрыто тестом `tests/unit/envProcessManager.test.ts` (сценарий «PID переиспользован»: посторонний живой процесс под записями с чужой идентичностью, старой без идентичности и неизвестной). Если вернуть в `stopProcess` проверку только через `kill(pid, 0)`, тест падает.
- Живая проверка через stdio-клиент MCP SDK на копии реестра хаба: `pack-win-72c` и `shot-81b` получили статус `dead`, `stop_process` их процессы (`conhost.exe`, `backlog.exe`) не тронул. Первый `list_processes` удалил 49 записей старше 7 дней за 20 мс.
- `list_processes`, `start_process` и `stop_process` стоят один запуск PowerShell (~0,25 с), но только если у записей есть живые pid.
- Формат ответа `listProcesses()` изменился: `{ processes, pruned }` вместо массива; `stopProcess()` возвращает `{ name, pid, status, killed }`. Модули используются только `env-server.mjs` и тестом.
- `list_processes` теперь меняет реестр (чистка) — это осознанно, см. Context.
- Старые записи, чей pid занят процессом, созданным раньше записи, остаются `unknown`, пока pid не освободится. После этого они получают статус `dead` и через 7 дней удаляются.
- Тот же паттерн есть в самом приложении: `electron/services/processManager.ts` (`stopEnvToolsProcess`, `listProcessesForProject`) и `electron/services/projectScanner.ts` читают этот реестр и проверяют pid только через `kill(pid, 0)`. Исправление — TASK-111, поле `pidCreatedAt` для этого подходит напрямую; решение — [[decision-60]].
- ProjectTemplate получает тот же код; проекты, развёрнутые из шаблона, — только после повторной синхронизации `scripts/env/`.
- Реализация — TASK-110. Связано: [[decision-58]], [[decision-37]], [[decision-57]].
