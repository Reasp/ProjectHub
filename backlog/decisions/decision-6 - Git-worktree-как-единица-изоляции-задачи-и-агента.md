## Context

Несколько агентов и человек одновременно работают над одним проектом. Общий рабочий каталог
приводит к конфликтам незакоммиченных изменений, к «чужим» файлам в диффе и к невозможности
запустить два dev-сервера. Рассматривались: клонирование репозитория под каждую задачу
(дорого по диску и времени, теряется общий объектный store), работа в одной ветке с
последовательной очередью агентов (нет параллельности), контейнеры на задачу (тяжело для
локального десктопа на Windows).

## Decision

1. **Единица изоляции это git worktree**: `<project>/.worktrees/<slug>` с собственной веткой.
   Для задачи ветка называется `task/<id>`, для участника Swarm `swarm/<sessionId>/<agentSlug>`,
   для Handoff-конвейера `handoff/<sessionId>`. Каталог `.worktrees/` автоматически добавляется
   в `.gitignore` и исключается из сканера git-статуса.
2. **Связь задача ↔ ветка ↔ worktree выводится из имени** по шаблону `task-<N>`. Это
   позволяет любому инструменту (CLI, агент, PR Hub) восстановить связь без дополнительного
   реестра. Обратная ссылка (URL PR, имя ветки) при этом должна дописываться в файл задачи.
3. **Каждый worktree получает свой контекст выполнения**: терминал и PTY с `cwd` в worktree,
   процессы и dev-сервер с отдельным профилем и портом, агент, запущенный именно в этом каталоге.
   Приложение должно уметь переключать «активный worktree» для доски, Git-панели и AI Studio
   (см. [[decision-15]]).
4. **Жизненный цикл**: создание из карточки задачи или при старте агента; завершение через
   диалог с диффом и слиянием (или PR); удаление worktree и ветки после слияния; сборка мусора
   осиротевших worktree и веток при старте приложения и по кнопке.
5. **Результат работы в worktree должен быть материализован в git** до того, как worktree
   удаляется (см. [[decision-8]]). Удаление с `--force` без коммита или снапшота запрещено.

## Consequences

- Плюс: дешёвая параллельность, общий объектный store, привычные git-инструменты для ревью.
- Минус: worktree не изолирует окружение (node_modules, порты, env). Для этого нужны
  per-worktree профили процессов, что является отдельной работой (TASK-62).
- Минус: на Windows длинные пути и блокировки файлов затрудняют удаление worktree; сервис
  обязан переживать `EBUSY` и предлагать повтор, а не терять данные.
