## Context

Жалоба владельца (TASK-120): описание задачи в окне задачи ProjectHub выглядит сплошной стеной
текста. Пример — TASK-315 в WorldSim: метки `**Исполнитель:**`, `**Почему:**`, `Цель:` идут подряд в
одной строке файла. `MarkdownViewer` заголовки, списки и абзацы показывает, но в самом тексте их
нет: агенты пишут описание одной строкой, потому что ни промпт планировщика
(`buildPlanInstructions` в `electron/services/planSchema.ts`), ни правила агентов (`infra-dev.md`)
формат описания не задавали. В примере плана описание было строкой «Что сделать и в каких файлах».

Рассмотренные варианты:

1. **Переписывать файлы задач** (скриптом или при открытии). Отвергнут: ProjectHub правил бы чужие
   файлы без спроса, в git появлялись бы изменения, которых никто не делал, а эвристика иногда
   ошибается — ошибка оставалась бы в файле навсегда.
2. **Кнопка «Отформатировать» через модель.** Отложен: результат лучше эвристики, но нужен вызов
   модели и проверка человеком, а жалоба касается всех уже существующих задач сразу. Можно добавить
   позже поверх этого решения.
3. **Структурировать при показе + требовать разметку от агентов.** Выбран.

## Decision

1. Чистая функция `structureTaskDescription` (`src/utils/taskDescriptionFormat.ts`) превращает
   сплошное описание в разметку только для отображения в окне задачи. Файл задачи и режим
   редактирования показывают исходный текст.
2. Функция срабатывает только на описании из одного абзаца без блоков Markdown (заголовков,
   списков, цитат, таблиц, кода, HTML). Описание с разметкой или несколькими абзацами автор оформил
   сам — его не трогаем.
3. Жирные метки `**Метка:**` / `**Метка**:` и простые метки из 1–3 слов с заглавной буквы и
   двоеточием в начале предложения становятся заголовками `###`. Связки («Например:») и метки с
   цифрами («Шаг 2:») заголовками не становятся. Код в обратных кавычках и ссылки защищены от разбора.
4. Текст длиннее 280 символов делится на абзацы по границам предложений.
5. Промпт планировщика требует описание подзадачи в Markdown с разделами `###` и списками; пример
   плана показывает такое описание. Правило 5 `infra-dev.md` требует того же от всех агентов.

## Consequences

- Старые задачи всех проектов сразу читаются лучше, без правки файлов и без вызова модели.
- Эвристика не знает смысла: простая метка вроде «Причина простая:» тоже станет заголовком. Цена
  ошибки низкая — меняется только показ, исходник доступен в режиме редактирования.
- Вне окна ProjectHub (CLI Backlog.md, git, веб-интерфейс Backlog.md) сплошное описание остаётся
  сплошным, поэтому требование к агентам — основная мера, а структурирование при показе — страховка.
- Реализация — TASK-120.
