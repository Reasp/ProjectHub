# Векторный RAG для документации проекта

Этот документ описывает, как в проекте организован смысловой поиск по документации — и для человека, и для агента. Это отдельная система от **GitNexus**: GitNexus строит граф кода (вызовы, зависимости, impact-анализ), а этот RAG — семантический индекс по markdown-документам в `backlog/docs/` и `backlog/decisions/`.

---

## 1. Архитектура и компоненты

- **Эмбеддинги**: локальная многоязычная модель `Xenova/multilingual-e5-small` через `@huggingface/transformers` (квантованная `q8`, ~120 МБ), работает полностью автономно без внешнего API. Документация проекта на русском, поэтому англоязычная `all-MiniLM-L6-v2` заменена (TASK-47): на русских запросах она возвращала нерелевантные чанки. Для семейства E5 обязательны префиксы `query: ` / `passage: ` — они хранятся в `meta.json` индекса и подставляются автоматически.
- **Реестр моделей**: `scripts/rag/embed.mjs` (`MODELS`) и его зеркало в `electron/services/ragSearch.ts`. Поддерживаются `Xenova/multilingual-e5-small` (по умолчанию), `Xenova/paraphrase-multilingual-MiniLM-L12-v2`, `Xenova/all-MiniLM-L6-v2`. Другую модель из реестра можно выбрать переменной окружения `RAG_EMBEDDING_MODEL` при сборке индекса.
- **Одна модель для индекса и запросов**: имя модели и префиксы записываются в `.rag-index/meta.json`; MCP-сервер, CLI и ProjectHub читают их оттуда, а не из константы в коде. Так индекс чужого проекта, собранный другой моделью, всё равно ищется корректно.
- **Векторная база**: [LanceDB](https://lancedb.github.io/lancedb/), хранится в каталоге `.rag-index/` и коммитится в Git (~300 КБ).
- **Кэш модели**: `.rag-cache/` (в `.gitignore`); приложение ProjectHub хранит модели в `userData/models`.

### Разбиение на чанки (`scripts/rag/chunk.mjs`)

- YAML frontmatter в индекс не попадает, из него берётся только `title` как контекст документа.
- Текст режется по заголовкам; для каждого чанка хранится путь заголовков от корня («хлебные крошки»: `Раздел › Подраздел › Пункт`). Заголовок без собственного текста отдельным чанком не становится, а попадает в путь дочерних чанков.
- Соседние мелкие блоки под одним родителем (например, `#### Назначение` из одного предложения и следующий `#### Функции`) склеиваются в один чанк.
- Кодируется `title › путь заголовков` + текст, а показывается только текст: так вектор «знает» контекст, а выдача остаётся читаемой.
- Встроенные картинки `data:image/...;base64,...` и длинные base64-блобы вырезаются (остаётся alt-текст и маркер `data-uri`). До этого один документ с иконками давал ~950 чанков base64-мусора из ~1000.
- Длинные блоки режутся на куски до 1000 символов по границам абзацев с перекрытием 150 символов.
- Версия алгоритма (`CHUNKER_VERSION`) пишется в `meta.json`: при её изменении `check-index` требует пересборки.

### Формат `.rag-index/meta.json`

| Поле | Назначение |
|---|---|
| `model`, `queryPrefix`, `passagePrefix` | модель и префиксы, которыми собран индекс; ими же кодируются запросы |
| `chunkerVersion` | версия чанкера, см. выше |
| `docsHash` | sha256 путей и содержимого всех `.md` в `backlog/docs/`, `backlog/decisions/` (переводы строк нормализованы, чтобы `autocrlf` не ломал сравнение) |
| `files`, `chunks`, `builtAt` | список проиндексированных файлов, число чанков, время сборки — их показывает карточка проекта в ProjectHub |

## 2. Основные команды

```bash
npm run index-docs                 # (пере)собрать векторный индекс из backlog/docs/**, backlog/decisions/**
npm run check-index                # проверить, актуален ли .rag-index относительно документации (exit 1, если нет)
npm run rag-search -- "запрос"     # быстрый семантический поиск из терминала
npm run rag-server                 # запуск MCP-сервера docs-rag для AI-агентов (stdio)
```

## 3. Когда перестраивать индекс

Индекс нужно пересобирать (`npm run index-docs`) и коммитить вместе с документами после **любых** правок в `backlog/docs/**/*.md` или `backlog/decisions/**/*.md`: добавления, удаления или изменения текста. Задачи (`backlog/tasks/`) в индекс не входят.

Забыть об этом сложно — актуальность проверяется автоматически по `docsHash`:

- `npm run lint:docs` (обязателен перед каждым коммитом, см. правило 15 в `infra-dev.md`) запускает `check-index` и **падает**, если индекс устарел, отсутствует или собран другой версией чанкера. В сообщении перечисляются новые и удалённые файлы.
- `npm run build` (и `pack:win`) запускает `check-index --warn` — только предупреждает, чтобы сборка приложения не блокировалась правками документации посреди задачи.
- Если `features.docsRag = false` в `infra.config.json`, проверка пропускается.

Первый запуск `index-docs` скачивает модель (~120 МБ) в `.rag-cache/`; повторные сборки на 9 документах занимают около минуты.

## 4. MCP-инструменты для AI-агентов

Сервер `scripts/rag/rag-server.mjs` регистрируется в `.mcp.json` под именем `docs-rag` и предоставляет следующие инструменты:

- `search_docs(query, topK?)`: смысловой поиск с возвратом наиболее релевантных фрагментов документации (файл, путь заголовков, текст чанка).
- `list_docs()`: список всех проиндексированных файлов базы знаний.
- `get_doc(file)`: чтение полного содержимого документа.

Проверка качества после перехода на многоязычную модель (2026-09-07): запросы «уязвимость MCP-сервера», «как работает Human-in-the-loop для Claude CLI», «почему выбран Electron а не Tauri», «как перестроить векторный индекс документации» возвращают в топ-3 разделы doc-6/doc-7 «Безопасность», doc-8, doc-3/decision-1 и doc-5 соответственно. На старой модели те же запросы возвращали пустые заголовки и разделы про иконки.
